## 1. Purpose

`v0.4.0-a1` to `v0.4.0-a8` delivered the Structural Version Control features one increment at a time. `v0.4.0-rc1` adds **no feature**. It turns them into one coherent public release:

- prepare, then freeze, every public contract of v0.4, except Structural Watch v1 and Watch Event Schema v1, which stay experimental;
- make the CLI, the exit codes and the errors consistent across commands, where this does not break a v0.1–v0.3 contract;
- harden security, cross-platform behavior and performance against written gates;
- publish user documentation, a reproducible showcase, and the release artifacts;
- then soak the RC on real repositories before `v0.4.0` (§12.15).

The freeze takes effect in the freeze commit of the release branch (gate G2). After it:

- an incompatible change to a frozen output needs a new contract version;
- an incompatible change to identity semantics, observation included, **needs a new fingerprint version** (D13).

A CHANGELOG entry is still required, but it never replaces the version change.

### 2.2 Error taxonomy and exit codes (§12.10)

| Command | Exit codes |
| --- | --- |
| root (tree), `fingerprint`, `snapshot` | 0 / 1 runtime error / 2 usage — the v0.1–v0.3 contract; an internal error exits 1 ✔ |
| `verify`, `diff` | 0 / 1 mismatch or differences / 2 / 3 / 4 / 5 / 6 |
| `history`, `watch` | 0 / 2 / 5 / 6 |

Inconsistencies, all to be confirmed in LOT 0:

- **The same failure gets different outcomes:**
  - a missing root: exit 1 in `fingerprint`; exit 5 with `source_read_failure` in `verify` and `diff`; exit 5 with `watch_root_unavailable` in `watch`;
  - a stdout write failure: 1 or 5;
  - an internal error: 1 or 6;
  - a configuration read failure: 1 in `fingerprint` and `snapshot`, 2 in `watch`.
- **Fallback codes carry a per-command prefix:** `verify_*`, `diff_*`, `history_*`, `watch_*`.
- **Codes and statuses do not always match the docs:**
  - an internal-flagged snapshot error keeps a code documented under exit 3 or 5;
  - `artifact_invariant_violation` is not flagged internal;
  - five codes are produced but documented nowhere;
  - `snapshot_internal_failure` is never built.
- **Some failures have no machine-readable form:** usage errors (exit 2) have no machine code, even with `--format json`, and `fingerprint --format json` writes nothing on failure.
- **Missing and stale definitions:**
  - the §12.10 categories are defined nowhere;
  - source, filesystem and Git failures all share exit 5;
  - `internal/cli/root.go:85-86` still says "0 success, 1 runtime error, 2 invalid arguments" ✔.

### 2.3 CLI consistency (§12.2)

- **Help lists refused flags:** `--config`, `--no-config` and `--no-user-config` appear in the help of `verify`, `diff` and `history`, which refuse them at runtime ✔ (`internal/cli/verify.go:87-99`).
- **Presentation flags behave in three ways:**
  - accepted and ignored: `fingerprint`, `snapshot`;
  - hidden and refused with a reason: `watch`;
  - "unknown flag": `verify`, `diff`, `history`.
- **`--format`:**
  - an invalid value gets a plain error in four commands, but the list of valid values in two;
  - `snapshot` has no `--format`.
- **Wording drift:**
  - `--no-moves` has three wordings;
  - rejection messages differ in wording and separators;
  - `--dirs-only` and `--depth` are worded differently across commands.
- **Operands:**
  - only `watch` refuses `git:`, `snapshot:` and `live:` operands;
  - `verify` takes a bare snapshot path where `diff` needs `snapshot:`.
- **No repository selector** for `git:` sources and `history`: they use the current directory only.
- **Help defects:**
  - a TAB-indented example in the root help;
  - no help topic for the v0.4 commands or for exit codes.

### 3.1 Review corrections applied

1. **Gate order.** The draft required the user acceptance of the official draft binaries before the tag that produces them. §5 now separates the pre-tag and post-tag gates. Tagging, publishing and starting the soak each need their own GO.
2. **Freeze timing.** LOT 1 now only **prepares** the freeze. The effective freeze happens after LOTs 2–4, in the freeze commit of the release branch (gate G2): first check that the corrections did not invalidate any contract, then publish the definitive contract register in that commit.
3. **D13.** The "explicit major note" alternative is removed. After the freeze, an incompatible identity change requires a new fingerprint version.

### 3.2 Technical policies requested by the review

**D6 — snapshot resource bounds (LOT 2).** LOT 2 specifies and tests, together:

- a strict limit on the bytes read, enforced **before** any full allocation (reading through a bounded reader instead of `io.ReadAll`);
- rejection of documents nested too deep and of abnormally large collections (node count, path length, `ignore` list, `requiredFeatures`);
- a stable error code for exceeding a limit, distinct from a read error: an over-limit document is an invalid snapshot, while an I/O failure is a read error;
- memory measurements (peak and retained) on valid and malformed documents close to the limit, through decoding, validation, Go structures and canonical projection.

The limit values are fixed only from these measurements. 256 MiB is not frozen beforehand.

**D7 — panic policy in two levels.**

1. **Primary:** remove panic sources with input validation, adversarial tests and the fuzz campaign (LOT 5). This includes an audit of type assertions, indexing and nil dereferences on input paths.
2. **Secondary:** a guard at the CLI boundary (`cli.Execute`) for recoverable failures that still get through. Its limits:
   - it does not catch panics in other goroutines (`gitsource` batch reader, watch engine); those must be handled in their goroutine or by design;
   - it cannot replace a stream that is already partly written with a complete error document.

The error stays visible, with the internal-error exit of the command. Machine outputs never carry a stack trace, and an incomplete output never ends as a success.

**D8 — performance decisions with numbers (LOT 6).**

- Fix a **reference machine**, documented: OS, CPU, memory, Go version.
- Keep the **distribution** of each measurement (repeated runs, `benchstat`-style comparison), not just one value.
- Define an **investigation threshold**, for example 20% on a reproducible benchmark. It triggers a manual review, not an automatic rejection.
- Record everything in `docs/benchmarks/v0.4-rc1.md` before the tag.

**D9 — fuzz campaign (LOT 5).**

- Targets are the untrusted inputs: snapshot bytes, diff source expressions, Git refs (new fuzzer), Git objects and trees, the configuration file, NDJSON parsing and canonical paths.
- Each target runs for a fixed duration with a recorded corpus and seed, so the campaign is reproducible.
- The results (duration, executions, crashes, fixes) go into the RC record.

### 5.1 RC soak protocol (D14)

- **Duration:** at least **seven days** after G6, and not before every scenario below has actually been exercised.
- **Profiles** (roadmap §12.15): small Go CLI, TypeScript monorepo, Flutter project, large repository, repository with symlinks, repository with deep Git history, Windows-heavy repository.
- **Recorded per profile and run:** OS and version, exact binary version and checksum, commands run (`fingerprint`, `snapshot`, `verify`, `diff` including `git:` and moves, `history`, `watch`), result, anomalies, and relevant measures (time, peak memory, node count).
- **Blocking for the stable release:** any contract bug, structural correctness error, or significant regression on a main workflow.
- **Deferrable with a written justification:** non-critical UX improvements.
- **Output:** a soak report with an incident table, classified by the §12.15 categories.

## 6. Out of scope

- New features, and any change to watch semantics beyond what its contract already states: watch stays experimental and outside the freeze.
  - Under D3, `watch` would report an unsupported entry with `unsupported_node_type`, an observation code that `watch-event-v1.md` already lists.
  - Reporting it for entries that were observed as files until now is still an **observable behavior change** (second CTO review). LOT 0 measures that impact.
- Renumbering the v0.1–v0.3 exit codes (D2).
- Independent cryptographic signing of the binaries (D10): the v0.4 trust chain is checksums, SBOM and attestations, documented as such.
- JSON Schema files, unless LOT 1 decides otherwise by contractual value (D12).
