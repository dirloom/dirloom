## 1. Purpose

`v0.4.0-a4` answers:

```text
what exactly changed?
```

`v0.4.0-a5` answers:

```text
what moved?
```

A5 turns some `REMOVED` + `ADDED` sets into one first-class `MOVED` change
when a deterministic, explainable, conservative rule establishes a unique
structural correspondence without reading file contents. When it cannot, the
A4 output stays as is.

A `MOVED` is a structural correspondence under `structural-v1`, not proof
that the filesystem object was actually moved. Without contents or history, a
deleted file and an unrelated new file with the same name, kind, and target
are indistinguishable. This limit is part of the public contract, especially
for `evidence: name`.

A5 MUST NOT modify:

- Fingerprint v1
- Identity Projection v1
- Canonical Identity Encoding v1
- Snapshot Schema v1
- Snapshot Artifact Projection v1
- Capture Semantics v1
- Verify Result Schema v1
- verify and diff exit codes, statuses, and diagnostic codes
- the A4 merge (`mergeRecords`) and the meaning of `ADDED`/`REMOVED`/`CHANGED`

A5 MUST NOT add:

- a second scanner, fingerprint engine, or snapshot validator
- content hashing or any file read
- similarity scores, percentages, or tunable thresholds
- a `RENAMED` or `COPIED` operation
- a Git source
- live↔live diff (stays a usage failure, exit 2)
- colors, icons, themes, output files, or clipboard support

## 5. Move Detection `structural-v1` (normative content for LOT 1)

### 5.1 Definitions

For each source tree T (A or B), built from its Identity Projection v1
records:

- `name(n)` = `Path.Base()`, canonical NFC;
- `state(n)` = kind plus target for target-carrying kinds (explicit presence);
- `children(n)` = records whose `Path.Parent()` is `n`, ordered by name bytes;
- `shape(n)` = exact interning of `(state(n), [(name(c), shape(c)) for c in
  children(n)])`. The node's own name is excluded, so shape is
  rename-invariant. A single intern table is shared by A and B so shape IDs
  are comparable. IDs are internal and never emitted;
- interning key: an unambiguous length-prefixed encoding of the state code,
  the target (when present), and, per child, its name and its already
  assigned shape ID. The key holds the children's IDs, never their subtree
  representation, so it costs O(children + child-name bytes) per node. A hash
  may bucket keys, but equality is always decided on the full key: a
  collision can never merge two shapes;
- `size(n)` = 1 + Σ `size(c)`;
- `key(n)` = `(name(n), shape(n))`;
- counts over all non-root nodes of each tree: `countA.key`, `countB.key`,
  `countA.shape`, `countB.shape`;
- `CA` = paths `REMOVED` by the A4 merge, `CB` = paths `ADDED`.

### 5.2 Pairing rules

A pair `(p, q)` with `p ∈ CA` and `q ∈ CB` is accepted if and only if exactly
one rule holds:

- **R1 Relocation**: `key(p) == key(q)`, `countA.key == 1`,
  `countB.key == 1`. (`parent(p) != parent(q)` follows from `p ∉ B`.)
- **R2 Rename in place**: `parent(p) == parent(q)`, `name(p) != name(q)`,
  `p` is a directory with at least one child, `shape(p) == shape(q)`,
  `countA.shape == 1`, `countB.shape == 1`.

R1 and R2 cannot both pair the same node, and global uniqueness makes pairing
one-to-one and independent of iteration order. The proof sketch goes in the
contract and a property test asserts it.

### 5.3 Absorption and emission

- Identical shapes mean that every descendant of `p` has a counterpart at the
  same relative path under `q`. Any descendant pair is at those corresponding
  positions.
- Process accepted pairs in A record order. An ancestor always sorts before
  its descendants, so no depth sort is needed. A pair is a **root pair**
  unless `p` is already marked as absorbed. A root pair marks the whole
  A-subtree of `p` and the whole B-subtree of `q` as absorbed. Total cost is
  O(N+M).
- Emit one `MOVED` per root pair: `path = q`, `from = p`,
  `before = after = state(p)`, `nodes = size(p)`,
  `evidence = subtree` if `p` has children, else `name`.
- Drop every absorbed record from `REMOVED` and `ADDED`. `CHANGED` entries
  are untouched. Sort all changes by `path` (UTF-8 bytes).

### 5.4 Invariants

| ID | Invariant | Checked by |
| --- | --- | --- |
| I1 | Lossless relative to the projections: given the A and B records, expanding each `MOVED` into `REMOVED` (A-subtree of `from`) and `ADDED` (B-subtree of `path`) yields exactly the `--no-moves` change list. The v2 document alone does not list absorbed descendants. | property + fuzz |
| I2 | One-to-one: each A path at most once among `REMOVED.path` ∪ `MOVED.from`; each B path at most once among `ADDED`/`CHANGED`/`MOVED.path` | validator |
| I3 | No nesting: no `REMOVED` path or `MOVED.from` below another `MOVED.from`; no `ADDED` path or `MOVED.path` below another `MOVED.path`; `from` and `path` of one move are not ancestor/descendant of each other | validator |
| I4 | Symmetry: `diff(B,A) == invert(diff(A,B))`, where invert swaps `ADDED`/`REMOVED`, `before`/`after`, and `MOVED.path`/`from` | property |
| I5 | Determinism: byte-identical text and JSON across runs, map iteration orders, and platforms | property + CI matrix |
| I6 | `moveDetection: none` ⇒ no `MOVED`; the `changes` array and `added`/`removed`/`changed` counts equal A4's (checked against the frozen v1 goldens) | validator + golden |
| I7 | `total = added + removed + changed + moved = len(changes)` | validator |
| I8 | `MOVED`: `from != path`, `before == after`, `nodes ≥ 1`, `evidence = name ⇔ nodes == 1`, `subtree ⇒ kind directory` | validator |
| I9 | Root `.` never appears as `path` or `from` | validator |

### 5.5 Complexity argument

Kept separate from the benchmarks, which only confirm it empirically. Let
N and M be the record counts, and L the total name bytes:

- tree index: one map insertion and one parent lookup per record, O(N+M);
- shapes: one reverse-order pass. Each node's key holds its children's IDs,
  and every node is a child exactly once, so total key bytes are O(N+M+L);
- counts: one map increment per node for `key` and one for `shape`, O(N+M);
- pairing: one lookup per `CA` node, O(N);
- absorption: each record is marked at most once, because accepted root pairs
  cover disjoint subtrees, O(N+M);
- validator: ancestor walks with set lookups, linear in total canonical path
  bytes, the same order as the input itself.

There is no candidate × candidate step. Repeated keys are rejected by
counting, never by comparing candidates with each other.

## 6. Internal architecture changes

```text
Source A ─┐                         ┌─ text renderer
          ├─ Compare (A4 merge) ─ MoveDetector ─ StructuralDiff ─┤
Source B ─┘   unchanged            structural-v1   (validated)     └─ JSON v2 encoder
```

- `internal/comparison/shape.go`: tree index from records (path → index,
  parent, children), reverse-order iterative shape computation (parents sort
  before children, so no recursion), shared intern table, counts.
- `internal/comparison/moves.go`: `detectMovesStructuralV1(recordsA,
  recordsB []identity.Record, changes []Change) []Change`, a pure function.
  It never observes a source and does no I/O.
- `Compare` gains an options value (`Options{MoveDetection}`); the merge stays
  byte-for-byte identical. With `MoveDetectionNone` the detector is not
  called.
- `internal/app/diff.go`: `DiffRequest.MoveDetection`, passed through.
- `internal/cli/diff.go`: `--no-moves`; `diff_result.go`: v2 encoder and
  `MOVED` text section.

## 9. Machine-output changes — Diff Result Schema v2

- Top level unchanged except `schemaVersion: 2`.
- `metadata`: `comparisonVersion` (1), `identityProjectionVersion` (1),
  `moveDetection` (`structural-v1` | `none`).
- `summary`: `added`, `removed`, `changed`, `moved`, `total` in that order.
- Change fields in encoder order: `path`, `operation`, `from`, `before`,
  `after`, `evidence`, `nodes`.

| Field | Presence |
| --- | --- |
| `path` | always; destination for `MOVED` |
| `operation` | `ADDED`, `REMOVED`, `CHANGED`, `MOVED` |
| `from` | `MOVED` only |
| `before` | `REMOVED`, `CHANGED`, `MOVED` (node existed in A) |
| `after` | `ADDED`, `CHANGED`, `MOVED` (node exists in B) |
| `evidence` | `MOVED` only: `subtree` or `name` |
| `nodes` | `MOVED` only: records covered, root included |

- Failure documents identical to v1 except `schemaVersion: 2`.
- A v2 success document is not self-sufficient for reconstruction: a
  `MOVED` gives `nodes` but not the absorbed descendant paths and states.
  The contract says so and points to `--no-moves` for the per-path list.
- `changes` stays `[]` when empty, never null. `EscapeHTML(false)`, two-space
  indent, final newline.

## 10. Error semantics

No new status, exit code, or diagnostic code. A `MOVED`-only result is
`DIFFERENCES` (exit 1, empty stderr). A detector or validator invariant
violation is `INTERNAL_ERROR` (exit 6, `diff_internal_failure`). The detector
does no I/O and cannot produce operational errors.

## 11. Security considerations

- No new input surface beyond one bool flag; no file contents read; symlink
  targets stay opaque strings and are never followed.
- Resource bounds: time and memory O(N+M) plus total name bytes for interning
  keys. There is no pairwise candidate comparison, so adversarial trees
  (thousands of identical generated folders, deep chains, wide fan-out)
  cannot trigger quadratic behavior. The argument is §5.5. The LOT 8
  benchmarks only confirm it empirically.
- Iterative shape computation: no recursion depth exposure on deep paths.
- Source identifiers are never emitted: no absolute source root, source
  expression, host, user, or date. A symlink or junction `target` is
  emitted as Identity Projection v1 records it, exactly as in A4, so it can
  be absolute when the link points outside the source root. A5 adds no new
  path data: `from` and `path` are canonical relative paths.

## 12. Cross-platform considerations

- Names and paths come from canonical NFC Identity Projection v1 paths, so
  shapes are platform-independent for identical artifacts.
- Case-only directory renames on Windows/macOS appear as distinct canonical
  paths in A4. With a unique non-empty shape, R2 reports them as `MOVED`.
  Case-only file renames stay `REMOVED` + `ADDED`. Fixtures assert both.
- Junctions (Windows) behave like symlinks: target is part of shape.
- Determinism must hold on the Linux, Windows, and macOS CI jobs (goldens
  byte-identical).

## 15. Migration and backward compatibility

| v1 | v2 |
| --- | --- |
| `schemaVersion: 1` | `schemaVersion: 2` |
| `metadata` 2 fields | + `moveDetection` |
| `summary` 4 fields | + `moved`; `total` includes it |
| ops `ADDED`/`REMOVED`/`CHANGED` | + `MOVED` with `from`, `evidence`, `nodes` |

- Consumers that check `schemaVersion` fail loudly, never silently.
- `--no-moves` gives the A4 `changes` array and `added`/`removed`/`changed`
  counts unchanged inside the v2 envelope. It is not byte-identical to A4:
  `schemaVersion`, `metadata.moveDetection`, and `summary.moved` differ, and
  so does the human summary line (`0 moved`).
- A consumer that needs every changed path must use `--no-moves`. A default
  v2 document summarizes each moved subtree as one `MOVED` with `nodes`.
- `dirloom verify`, `snapshot`, `fingerprint` outputs are unchanged.

## 18. Explicit non-goals

- Parent inference for partially edited moved subtrees (candidate for a
  later strategy).
- Move combined with rename; file rename; case-only file rename.
- `COPIED` detection; many-to-one or one-to-many moves.
- Content hashing or any optional content strategy.
- Similarity scores, confidence percentages, tunable thresholds.
- Moves in `verify`, `snapshot`, or `fingerprint` output.
- Git sources, history, watch.
