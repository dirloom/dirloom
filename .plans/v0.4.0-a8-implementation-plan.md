## 1. Purpose

`v0.4.0-a4` to `v0.4.0-a7` compare and list structural states on request.
`v0.4.0-a8` reports structural changes as they happen in a local directory,
without running `dirloom diff` again:

```bash
dirloom watch
dirloom watch ./src --format ndjson
dirloom watch --preset monorepo --format ndjson | jq -c 'select(.event == "node.moved")'
dirloom watch --poll 2s --format ndjson        # network or virtual filesystem
```

```text
Watching structure (experimental, native): 1204 nodes, dlm:v1:sha256:8c1f0a3e94b2…
#1  + src/features/payments
#1  > src/shared/auth -> src/features/auth (subtree, 4 nodes)
#1  = 1205 nodes, dlm:v1:sha256:2b9e71c0d4aa…  (+1 -0 ~0 >1)
```

```json
{"schemaVersion":1,"event":"watch.started","generation":0,"metadata":{"watchVersion":1,"stability":"experimental","comparisonVersion":1,"identityProjectionVersion":1,"moveDetection":"structural-v1","backend":"native"},"capture":{"depth":null,"dirsOnly":false,"hidden":false,"useDefaultIgnores":true,"useGitignore":true,"ignore":[]},"fingerprint":"dlm:v1:sha256:<64 hex>","nodeCount":1204}
{"schemaVersion":1,"event":"node.added","generation":1,"path":"src/features/payments","after":{"kind":"directory"}}
{"schemaVersion":1,"event":"node.moved","generation":1,"path":"src/features/auth","from":"src/shared/auth","before":{"kind":"directory"},"after":{"kind":"directory"},"evidence":"subtree","nodes":4}
{"schemaVersion":1,"event":"state.changed","generation":1,"fingerprint":"dlm:v1:sha256:<64 hex>","nodeCount":1205,"summary":{"added":1,"removed":0,"changed":0,"moved":1,"total":2}}
```

Native notifications only tell `watch` when to look again, and a periodic
reconciliation catches what they miss. What `watch` reports always comes
from a full observation compared with the last reported state, through the
same engine as `fingerprint` and `diff`. It is the roadmap's "Experimental
Watch" (§11): explicitly `EXPERIMENTAL`, outside the v0.4 contract freeze.

The product guarantees structural transitions, verifiable synchronization
and bounded resources. It does not pretend to guarantee what the operating
systems do not: perfect notification delivery, atomic writes to stdout, or
cleanup time when Windows closes a console.

A8 MUST NOT modify:

- Capture Semantics v1, Identity Projection v1, Canonical Identity Encoding
  v1, Fingerprint v1, Snapshot Schema v1, Verify Result Schema v1, Diff
  Result Schema v3, Move Detection `structural-v1`, Git Tree Source v1,
  Structural History v1, History Result Schema v1
- the output, statuses or exit codes of any existing command: every existing
  test and golden stays green without being edited
- the global signal handling of `cmd/dirloom` (only `os.Interrupt` today)
- the configuration resolution shared with `fingerprint` and `snapshot`

A8 MUST NOT add:

- a second scanner, a second structural model, or events derived from raw
  OS notifications
- cgo, or a change to the release build (`CGO_ENABLED=0`)
- a Go module, unless the LOT 0 review selects `fsnotify` for a platform
  (then through the dependency review policy of `docs/dependencies.md`)
- a file written by `watch`: no cache, state file, lock or log
- a daemon, socket, HTTP or MCP transport, or several roots per process
- Git, snapshot or history sources in `watch`
- an automatic fallback from native notifications to polling

## 2. Existing-state inspection

Verified on `main` at `f6ed5b4` on 2026-11-01:

- No `watch` command, no notification code, no notification dependency.
  Direct modules: `cobra`, `git-pkgs/gitignore`, `go.yaml.in/yaml/v3`,
  `golang.org/x/sys` v0.47.0, `golang.org/x/term` v0.45.0,
  `golang.org/x/text` v0.41.0. `x/sys/windows` is used by
  `internal/output`, `internal/clipboard` and `internal/presentation`;
  `x/sys/unix` is not used yet (same module, no `go.mod` change needed).
- `cmd/dirloom/main.go`: `signal.NotifyContext(ctx, os.Interrupt)`, then
  `cli.Execute`. `SIGTERM` is not handled.
- `internal/cli/fingerprint.go`: capture flags `--root`, `--preset`,
  `--depth`, `--dirs-only`, `--hidden`, `--ignore`, `--no-default-ignore`,
  `--no-gitignore`; `--color`, `--icons`, `--theme` accepted and ignored;
  capture resolved by `resolveStructuralOptions` (flags, preset,
  configuration), then `app.Fingerprint(ctx, app.InspectRequest)`.
- `app.NewFilesystemSource(InspectRequest)` returns the `live:` source;
  `identity.ProjectV1`, `identity.FingerprintRecords` and
  `comparison.CompareRecords(recordsA, recordsB, refA, refB, opts)` (the
  last two added by A7), and `StructuralDiff.Validate()`, are what a watch
  cycle needs.
- `internal/tree.Scanner` builds the complete tree before returning, never
  follows links below the root, and returns no partial tree on error. An
  entry that disappears between `ReadDir` and `Info` fails the whole
  observation ("entry no longer exists", `source_read_failure`): under
  concurrent changes an observation can fail and must be retried. With
  `--depth 0` the scanner does not read the root at all.
- The filesystem source rewrites an absolute link target that points inside
  the root as root-relative; a target outside the root stays absolute and
  is emitted as such by Diff Result Schema v3 (ADR 0006).
- Default ignored directories: `.git`, `node_modules`, `.next`, `.nuxt`,
  `coverage`, `.cache`, `.turbo`. Hidden: a leading `.` on every platform,
  plus `FILE_ATTRIBUTE_HIDDEN` on Windows.
- Node kinds: `directory`, `file`, `symlink`, `junction` (Windows).
- Diff Result Schema v3 change object: `path`, `operation`, `from`,
  `before`, `after`, `evidence`, `nodes`; changes sorted by `path` as UTF-8
  bytes. Snapshot Schema v1 `capture` object: `depth`, `dirsOnly`, `hidden`,
  `useDefaultIgnores`, `useGitignore`, `ignore`.
- Diff text output uses `+`, `-`, `~`, `>` and `from -> path (evidence,
  nodes)`, with no ANSI.
- Exit codes: `fingerprint` uses 0/1/2 (pre-v0.4 style); `diff` and
  `history` use 5 for observation errors and 6 for broken invariants.
- Release builds: `CGO_ENABLED=0`, `windows`, `linux`, `darwin` on `amd64`
  and `arm64`.
- CI (`.github/workflows/ci.yml`): runs on pushes to `main` and
  `release/**` and on pull requests; a push to a feature branch alone runs
  nothing. Test matrix `ubuntu-26.04`, `windows-latest`, `macos-latest`;
  `-race` on `ubuntu-latest` only; shell exit-code tests for `verify` and
  `diff` in bash and PowerShell.
- A1 benchmarks (Windows, i7-10610U): 10k-entry scan 38 ms, full
  fingerprint of 10k entries 84 ms, 100k-entry in-memory pipeline 327 ms.
  A full re-observation per cycle is affordable up to about 10^5 entries.
- Lessons kept from A5–A7: contracts before code; facts checked on real
  systems before they become contract text; every helper linear in input
  size; no partial result presented as a success; `Close` never waits on a
  refused resource.

## 3. Decisions (summary of ADR 0008, revised)

| # | Question | Decision |
| --- | --- | --- |
| 1 | Command | `dirloom watch [<directory>] [--root <dir>] [capture flags] [--no-moves] [--debounce <duration>] [--poll <interval>] [--format text\|ndjson]`; filesystem only; capture resolved once at startup like `fingerprint`. |
| 2 | Truth | Notifications are signals. Every cycle observes the whole root and compares it with the last emitted state through `CompareRecords`; equal fingerprints emit nothing. |
| 3 | Reconciliation | Native mode observes in full whenever no observation succeeded for the reconciliation interval (60 s initially, tuned by LOT 9). Silent when unchanged; a difference no signal explains is reported in a rescan with reason `reconciliation`. |
| 4 | Relevance | A backend drops a notification only when it proves it cannot change the artifact; any doubt triggers an observation. Contract: content-only edits produce no structural event. Avoiding the observation is an optimization that depends on the backend. |
| 5 | Debounce | 200 ms of quiet, at most 10 × debounce under continuous activity; `--debounce` 10 ms – 10 s. |
| 6 | Watch sets | Structural set: root and captured directories the scanner entered (empty at `--depth 0`). Control set: what detects the loss of the root, at every depth. Registrations dropped on the backend's removal notice, reconciled after each observation, followed by a verification observation when they change. |
| 7 | Backends | Preferred: Windows recursive `ReadDirectoryChangesW` plus the root's parent, Linux inotify per directory, macOS kqueue per directory, on `golang.org/x/sys`. Conditional on the LOT 0 comparison with `fsnotify` (F19). `--poll <interval>` explicit, never automatic. |
| 8 | Filesystem policy | Native mode refuses a documented list of recognized network and virtual types (`watch_filesystem_unsupported`, suggests `--poll`). Unknown types and FUSE are accepted; sub-mounts are not checked; reconciliation bounds what is missed. |
| 9 | Rescans | Reasons `overflow`, `reconciliation`, `error`; never nested; closed by `rescan.completed`. |
| 10 | Observation errors | Non-fatal after the first state: `watch.error`, `rescan.started` (`error`), retry on signal and on a backoff from the debounce up to 5 s. |
| 11 | Fatal | Root removed, renamed or replaced; a required resource cannot be allocated; backend failure; recognized network or virtual filesystem in native mode; output failure; invariant. `watch.error` (fatal) then `watch.stopped`. |
| 12 | Publication | A generation is complete and validated before any of it is written. Writes to stdout are not atomic: a consumer commits a generation on its `state.changed` and discards one cut short. |
| 13 | Termination | Controlled interruption (Ctrl+C, `CTRL_BREAK_EVENT`, `SIGINT`, `SIGTERM` scoped to `watch`): abandon the cycle, close handles, `watch.stopped`, exit 0. Blocked stdout: at most a 2 s output grace period, then exit 5 without `watch.stopped`. Windows console close: best effort. |
| 14 | Backpressure | Flags instead of queues; one writer goroutine with at most one generation in flight; memory O(tree), independent of event rate and consumer speed. |
| 15 | Machine output | Watch Event Schema v1, NDJSON, ten events, `schemaVersion` on every line, no timestamps, no sequence numbers. |
| 16 | Formats | `text` (default, not a contract), `ndjson`; `json` refused. |
| 17 | Exit codes | 0 controlled interruption, 2 usage, 5 fatal observation/backend/output (grace period included), 6 internal; no 1, 3 or 4. |
| 18 | Privacy | Never the absolute root, host, user or time. Structural values of the artifact (an absolute link target outside the root) and user options (`capture.ignore`) are emitted as they are. Diagnostics disclose no local path outside the artifact. |
| 19 | Guarantees | Synchronization outside rescans; convergence within one reconciliation interval (native) or poll interval; diff equivalence per generation; structural equivalence across backends and platforms at quiescent checkpoints; serialization determinism of a given state and generation. ## 5. Structural Watch v1 (normative content for LOT 1, after the LOT 0 review)

### 5.1 Request

- Root: a positional directory or `--root`, not both (as `fingerprint`);
  default the current directory.
- Capture flags, preset and configuration file: exactly as
  `dirloom fingerprint`, resolved once at startup.
- `--no-moves`: Move Detection `none`.
- `--debounce <duration>`: Go duration syntax, 10 ms to 10 s, default
  200 ms. Native mode only.
- `--poll <interval>`: Go duration syntax, 100 ms to 1 h. Selects the
  polling backend. Refused with `--debounce`.
- `--format text|ndjson`, default `text`. `json` is a usage error whose
  message suggests `ndjson`.
- The reconciliation interval is not a flag in v1 (§5.6).
- Rejected (usage error, exit 2): `--color`, `--icons`, `--theme`,
  `--output`, `--copy`, any `git:`, `snapshot:` or `live:` operand, more
  than one directory.

### 5.2 Startup

1. Validate flags; resolve Capture Semantics as `fingerprint` does
   (configuration errors are usage errors, as there).
2. Resolve the absolute root, following a root link as the scanner does;
   record its file identity.
3. Native mode: apply the filesystem policy (§5.11); a recognized network or
   virtual type is fatal `watch_filesystem_unsupported`.
4. Start the backend with its control registrations (§5.4). Windows also
   opens the recursive root handle and issues the first reads; Linux and
   macOS create the inotify instance or kqueue and register the root.
5. Observe. A root that is missing, not a directory or unreadable is fatal
   at once (`watch_root_unavailable`). Any other failure is retried on the
   error backoff for at most 5 s, then it is fatal with its own code.
6. Linux and macOS: register the structural watch set of this state and
   mark the watcher dirty, so that a verification observation follows.
7. Publish `watch.started` with generation 0; start the reconciliation
   timer (native mode).

Registering before the first observation (Windows, and the root on every
platform) and verifying after registration (Linux, macOS) leave no window
in which a change is neither observed nor signalled by a working backend;
reconciliation covers a backend that does not work as expected.

### 5.3 Cycle

```text
state = startup observation (records, fingerprint, nodeCount); g = 0; rescan = closed
loop:
  wait for: a relevant signal, an overflow, a fatal signal, the retry timer,
            the reconciliation timer (native), the poll tick (polling), or cancellation
  cancellation          → stop(interrupted)
  fatal signal          → stop(error)
  overflow and rescan closed → publish rescan.started(overflow); rescan = open
  trigger = reconciliation if woken by its timer with nothing pending, else signal
  native and trigger = signal: wait for debounce of quiet, at most maxDelay since
                               the first pending signal
  clear the dirty and overflow flags
  root identity differs or root missing → fatal watch_root_unavailable
  observe the whole root
    failure → publish watch.error(fatal=false) unless already published for this code
              in this rescan; if rescan closed: publish rescan.started(error); rescan = open
              arm the retry timer (backoff); continue
  project, fingerprint; reset the backoff; restart the reconciliation timer
  if fingerprint != state.fingerprint:
    diff = CompareRecords(state.records, records, moves); diff.Validate() else INTERNAL
    if trigger = reconciliation and rescan closed:
      wait one debounce; if no relevant signal arrived since the observation started:
        publish rescan.started(reconciliation); rescan = open
    publish the node events of generation g+1 and state.changed(g+1)
    state = observed; g = g + 1
  native, per-directory backends: reconcile registrations with the new structural set;
    a change, a dropped registration, or a transient refusal → mark dirty;
    a refusal for a resource limit → fatal watch_limit_reached
  if rescan open and neither dirty nor overflow is pending → publish rescan.completed(g); rescan = closed

publish(x):   wait until the writer is idle (cancellation or fatal → stop), then hand x to it
stop(reason): close the backend; publish watch.error(fatal) if any, then watch.stopped(reason);
              wait for the writer at most the output grace period;
              on expiry: best-effort stderr diagnostic, exit 5
```

The reconciliation timer only runs while no cycle, retry or rescan is
pending, and restarts after every successful observation: it measures the
time since the last full observation. A generation is published only after
it is complete and validated. An observation interrupted by cancellation
publishes nothing.

### 5.4 Watch sets

- **Structural watch set** of a state: the root, unless `--depth 0`, plus
  every directory node of depth *d* < depth limit (all of them when
  unlimited): the directories the scanner entered. Ignored subtrees,
  default-ignored directories, hidden directories when hidden entries are
  excluded, links and junctions are never in it. Empty at `--depth 0`.
- **Control watch set**, at every depth: Windows, the non-recursive handle
  on the root's parent filtered on the root's name (none for a drive root,
  which cannot be removed or renamed); Linux, the root's inotify watch with
  `IN_DELETE_SELF` and `IN_MOVE_SELF`; macOS, the root's descriptor with
  `NOTE_DELETE`, `NOTE_RENAME` and `NOTE_REVOKE`. It never produces a
  structural event, only the fatal root condition. At `--depth 0` it is the
  only registration.
- On Linux and macOS each structural member is registered once. A
  registration is dropped on the backend's own removal notice
  (`IN_IGNORED`, `NOTE_DELETE`, `NOTE_RENAME`, `NOTE_REVOKE`), not only on
  an identity mismatch, because inode numbers can be reused at once; the
  drop marks the watcher dirty and the next reconciliation of registrations
  registers the path again.
- A rename of an ancestor of the root does not reach the control set; the
  identity check of the next observation (at the latest one reconciliation
  interval later) makes it fatal.

### 5.5 Relevance

A notification is relevant unless the backend proves otherwise:

| Notification | Relevant when |
| --- | --- |
| entry created, deleted, renamed or moved | its parent directory is in the structural watch set, or the rename cannot be resolved |
| content written, size, timestamps | the entry is named `.gitignore` in a structural directory and `.gitignore` files apply (case-insensitive on Windows and macOS) |
| attributes (Windows) | hidden entries are excluded and the entry's hidden attribute may disagree with its membership in the last state (narrowing by one `Lstat` allowed) |
| a directory changed, without names (kqueue `NOTE_WRITE`) | always |
| self deletion or move of a registered directory | always (dirty, re-registration) |
| control registration: root deleted, renamed or replaced | always (fatal) |
| overflow | always (rescan) |
| path not decodable, Windows short name, path outside the known tree | always |

The contract is that content-only edits produce no structural event.
Avoiding the observation is an optimization: tests assert zero observations
for content-only edits only on backends that report entry names (Linux,
Windows, and macOS if F7 shows `NOTE_WRITE` stays silent for them).
Dropping a relevant notification is a correctness bug; triggering an
unneeded observation is a cost.

### 5.6 Timing parameters

| Parameter | Value | Configurable |
| --- | --- | --- |
| Debounce (quiet time) | 200 ms | `--debounce`, 10 ms – 10 s |
| Maximum delay under continuous activity | 10 × debounce | no |
| Reconciliation interval (native) | 60 s initially; final value set by LOT 9 from F20 and the benchmarks | no |
| Error retry backoff | debounce (200 ms in polling mode), doubled after each failure, capped at 5 s | no |
| Startup observation retries | at most 5 s | no |
| Output grace period | 2 s | no |
| Poll interval | none in native mode | `--poll`, 100 ms – 1 h |
| Native read buffers | 64 KiB (Windows, Linux) | no |

### 5.7 Rescans and synchronization

- A rescan opens on an overflow, on a reconciliation difference that no
  signal explains, or on the first observation failure while no rescan is
  open. It closes with `rescan.completed` after the first cycle that
  observes successfully and leaves nothing pending.
- Rescans never nest. An overflow, a failure or a reconciliation difference
  during an open rescan keeps it open.
- Inside an open rescan the last emitted state may be stale; outside, it is
  the state of the last successful observation.
- Generations published during an open rescan are ordinary generations.

### 5.8 Fatal conditions

| Code | Condition |
| --- | --- |
| `watch_root_unavailable` | The root is missing, not a directory or unreadable at startup, or was removed, renamed or replaced during the run (control registrations, identity check at each observation) |
| `watch_limit_reached` | A resource the backend requires cannot be allocated: inotify instance or watch (`EMFILE`, `ENOSPC`), kqueue or descriptor (`EMFILE`, `ENFILE`), Windows handle or buffer; the message names the system setting when there is one |
| `watch_backend_failure` | Any other backend failure (handle invalidated, read error) |
| `watch_filesystem_unsupported` | Native mode on a recognized network or virtual filesystem (§5.11); the message suggests `--poll` |
| any observation code | The startup observation still failed after its retries |
| `internal_invariant_failure` | A generation failed validation, or the engine broke one of its invariants |

A fatal condition publishes `watch.error` (`fatal: true`) then
`watch.stopped` (`error`), closes every handle and exits 5 (6 for an
internal failure), within the output grace period (§5.9).

### 5.9 Termination

- **Controlled interruption:** Ctrl+C and `CTRL_BREAK_EVENT`
  (`os.Interrupt`), `SIGINT` and `SIGTERM` on Unix. The `SIGTERM` handler
  belongs to the `watch` command only. The engine abandons any observation
  in progress, closes the backend (inotify descriptor, kqueue and directory
  descriptors, Windows handles after `CancelIoEx`), waits for its
  goroutines, publishes `watch.stopped` (`interrupted`) and exits 0.
- **Blocked stdout:** a blocking write to a pipe cannot be interrupted
  portably. All writes go through one writer goroutine. When an
  interruption or a fatal condition arrives while the writer is blocked,
  `watch` waits at most the output grace period for it; on expiry it writes
  a best-effort stderr diagnostic and exits 5 without `watch.stopped`. The
  process always ends and releases its handles; the stream it leaves is
  visibly incomplete.
- **Closed stdout:** nothing more is written; Unix's default `SIGPIPE`
  applies; elsewhere exit 5 with a stderr diagnostic.
- **Windows console close, logoff and shutdown** (delivered by Go as
  `SIGTERM`): handled like an interruption, best effort only. Windows may
  end the process before `watch.stopped` is written.
- Stdin is never read.

### 5.10 Bounds and backpressure

- Backend goroutines only set the dirty, overflow or fatal flag and wake the
  engine without blocking; they keep draining kernel queues while the
  engine waits on the writer.
- The engine holds at most the last emitted state and the current
  observation (artifact, records), the two watch sets, the registrations and
  one encoded generation in flight.
- A slow consumer delays the next observation; everything that changed
  meanwhile is reported by the next generation against the last emitted
  state. No queue of events or notifications exists.
- Event volume per generation equals the `changes` of the equivalent
  `dirloom diff` (for example one `node.removed` per removed path).

### 5.11 Backends and filesystem policy

| Backend | Structural registration | Control registration | Signals | Overflow |
| --- | --- | --- | --- | --- |
| Windows | One recursive `ReadDirectoryChangesW` on the root (`FILE_LIST_DIRECTORY`, all share modes, backup semantics, overlapped I/O); filters file name, directory name, last write, and attributes when hidden entries are excluded | Non-recursive handle on the root's parent, filtered on the root's name | Relative paths from `FILE_NOTIFY_INFORMATION`, checked against the structural set | 0-byte completion or `ERROR_NOTIFY_ENUM_DIR` |
| Linux | One inotify watch per structural directory: `IN_CREATE`, `IN_DELETE`, `IN_MOVED_FROM`, `IN_MOVED_TO`, `IN_DELETE_SELF`, `IN_MOVE_SELF`, `IN_CLOSE_WRITE`, with `IN_ONLYDIR`, `IN_DONT_FOLLOW`, `IN_EXCL_UNLINK` | The root's watch with `IN_DELETE_SELF`, `IN_MOVE_SELF` (alone at `--depth 0`) | Watch descriptor → directory; names checked for `.gitignore` | `IN_Q_OVERFLOW` |
| macOS | One `O_EVTONLY` descriptor per structural directory, `EVFILT_VNODE` with `NOTE_WRITE`, `NOTE_DELETE`, `NOTE_RENAME`, `NOTE_REVOKE`, `EV_CLEAR`; one per `.gitignore` when `.gitignore` files apply | The root's descriptor with `NOTE_DELETE`, `NOTE_RENAME`, `NOTE_REVOKE` | Descriptor → directory or `.gitignore` | none (kqueue coalesces per descriptor) |
| Poll | none | none (identity check at each poll) | One observation per interval | none |

This table describes the preferred `x/sys` implementation; the LOT 0 review
may replace a platform's mechanism by `fsnotify` (Q1, F19), with the same
contract.

**Filesystem policy (native mode only).** The type of the filesystem
holding the root is checked against a list of recognized network and
virtual types, fixed by LOT 0 (F13) and published in the reference: Linux
`statfs` types (using the `x/sys/unix` constants), macOS `f_fstypename`
values, and Windows `GetDriveType` = `DRIVE_REMOTE`. A recognized type is
refused with `watch_filesystem_unsupported`. This is a classification of
known cases, not an exhaustive one:

- an unrecognized type is accepted, and so is FUSE;
- mount points below the root are not checked (F17);
- `GetDriveType` does not characterize every Windows storage arrangement.

In every such case, periodic reconciliation bounds how long a missed change
stays unreported. The classification function is unit-tested on canned
values for every recognized and several unrecognized types.

Every native buffer parser is bounds-checked record by record and fuzzed.
No descriptor or handle opened below the root follows a link
(`IN_DONT_FOLLOW`, `O_NOFOLLOW`).

### 5.12 Guarantees

- **Synchronization.** Outside a rescan, the last emitted state is the state
  of the last successful observation. Every rescan ends with
  `rescan.completed` or with the end of the stream.
- **Convergence.** If the tree stays unchanged and observations succeed, the
  last emitted fingerprint equals `dirloom fingerprint` of the root with the
  same Capture Semantics at the latest one reconciliation interval plus one
  observation after the last change (native), or one poll interval plus one
  observation (polling); usually within the debounce, when the backend
  delivers the notification.
- **Diff equivalence.** For each generation *g*, the node events are the
  `changes` of Diff Result Schema v3 between snapshots of states *g − 1*
  and *g* with the same Capture Semantics and move detection: same values,
  same order, `event: node.<operation in lower case>` in place of
  `operation`.
- **Structural equivalence.** For one scenario observed at quiescent
  checkpoints, every backend and platform reaches the same states
  (fingerprints, node counts) and the same net changes between consecutive
  checkpoints. `metadata.backend` and the grouping of changes into
  generations may differ.
- **Serialization determinism.** A given state and a given generation are
  serialized to the same bytes on every platform.
- **Not guaranteed:** exactly-once delivery, a log of filesystem
  operations, an order of operations inside a generation, a latency below
  the reconciliation interval when a backend misses a notification, move
  detection across two generations, atomic writes to stdout,
  `watch.stopped` after a blocked stdout or a Windows console close, the
  classification of every network or virtual filesystem.

### 5.13 Diagnostics

Non-fatal observation failures reuse `artifact.Error.Code`
(`source_read_failure`, `canonical_path_collision`, …), with
`watch_observation_failure` as the fallback. Fatal codes are listed in
§5.8. Messages name paths relative to the root and never disclose other
local paths (the absolute root, the home directory, temporary
directories); they are informative, not stable.

### 5.14 Publication

The engine computes and validates a whole generation before handing it to
the writer: an unvalidated change is never published. The writer flushes
after each generation and each control event, but stdout gives no
atomicity: a generation larger than `PIPE_BUF` may take several writes, and
a write may fail after transferring part of the data. A consumer therefore:

- commits a generation only when it has read its `state.changed`;
- discards a generation cut short by the end of the stream, including a
  last line without its line feed;
- treats a stream without `watch.stopped` as incomplete.

## 9. Machine output — Watch Event Schema v1

### 9.1 Encoding

- One JSON object per line, UTF-8 without BOM, compact (no indentation),
  HTML escaping disabled, terminated by one line feed (`\n`) on every
  platform; no blank line.
- Field order fixed by the encoder. Every line starts with
  `schemaVersion` (`1`) and `event`; `generation` follows on every line
  except those of a startup failure.
- Publication follows §5.14: validated generations, no atomicity on stdout.

### 9.2 Events

| `event` | Fields after `schemaVersion`, `event`, `generation` |
| --- | --- |
| `watch.started` | `metadata` {`watchVersion`: 1, `stability`: `experimental`, `comparisonVersion`: 1, `identityProjectionVersion`: 1, `moveDetection`: `structural-v1` \| `none`, `backend`: `native` \| `poll`}, `capture` (Snapshot Schema v1 Capture Semantics object, same field order), `fingerprint`, `nodeCount` |
| `node.added` | `path`, `after` |
| `node.removed` | `path`, `before` |
| `node.changed` | `path`, `before`, `after` |
| `node.moved` | `path`, `from`, `before`, `after`, `evidence`, `nodes` |
| `state.changed` | `fingerprint`, `nodeCount`, `summary` {`added`, `removed`, `changed`, `moved`, `total`} |
| `rescan.started` | `reason`: `overflow` \| `reconciliation` \| `error` |
| `rescan.completed` | `fingerprint`, `nodeCount` |
| `watch.error` | `fatal`, `diagnostic` {`code`, `message`} |
| `watch.stopped` | `reason`: `interrupted` \| `error`, `fingerprint` |

Node fields have exactly the presence rules, values and node-state objects
(`kind`, `target`) of Diff Result Schema v3 changes. `generation` is the new
generation on node events and `state.changed`, and the last committed
generation on every other event. On a startup failure, `watch.error` and
`watch.stopped` have no `generation`, and `watch.stopped` no `fingerprint`.

### 9.3 Stream grammar

```text
stream     = started { item } [ fatal ] stopped
           | fatal stopped                                   (startup failure)
item       = generation | rescan-started | rescan-completed | error
generation = node-event { node-event } state-changed
error      = watch.error(fatal=false) [ rescan-started(reason=error) ]
fatal      = watch.error(fatal=true)
```

A stream may also end anywhere without `stopped` (process killed, stdout
closed or blocked beyond the grace period); it is then incomplete.

### 9.4 Invariants (checked by the stream validator)

1. Every line parses as one object with `schemaVersion: 1` and a known
   `event`.
2. The first line is `watch.started` with generation 0, or a fatal
   `watch.error` followed only by `watch.stopped` (`error`).
3. Generations increase by exactly 1. The node events of a generation are
   contiguous, sorted by `path` as UTF-8 bytes, obey every Diff Result
   Schema v3 change rule, and are followed by its `state.changed`, whose
   summary counts them (`total` ≥ 1).
4. Each `state.changed` fingerprint differs from the previous state's.
5. Rescans never nest. `rescan.started` (`error`) directly follows a
   non-fatal `watch.error`; `rescan.started` (`reconciliation`) is directly
   followed by a generation; `rescan.completed` carries the last state's
   fingerprint and node count.
6. At most one fatal `watch.error`, directly followed by `watch.stopped`
   (`error`). `watch.stopped` is the last line; with `interrupted`, no
   fatal error precedes it. Its fingerprint is the last state's.
7. A consumer commits a generation on its `state.changed` and discards a
   trailing incomplete generation (§5.14).

### 9.5 Evolution and experimental policy

Consumers ignore fields they do not know, treat unknown diagnostic codes
and rescan reasons as opaque, and skip lines whose `event` they do not
know. Additive within v1: a new optional field, a new diagnostic code, a
new rescan reason, a new event that a consumer may skip without losing
track of the state. A new schema version is required for: removing or
renaming a field, changing a meaning, type, presence rule or order, a new
node event, or a change of exit codes. Because the stream is experimental,
such a change may ship in any v0.x release, with the new `schemaVersion`
and a CHANGELOG entry; it is never silent.

## 10. Error semantics

| Outcome | stdout (`ndjson`) | stderr | Exit |
| --- | --- | --- | ---: |
| Controlled interruption | … `watch.stopped` (`interrupted`) | empty | 0 |
| Usage error | empty | `Error: …` | 2 |
| Fatal observation, backend or filesystem error | … `watch.error` (fatal), `watch.stopped` (`error`) | empty | 5 |
| Startup failure | `watch.error` (fatal), `watch.stopped` (`error`) | empty | 5 |
| Interruption or fatal condition with stdout blocked beyond the grace period | incomplete, no `watch.stopped` | best-effort `Error: …` | 5 |
| stdout write failure | truncated | `Error: …` | 5 (or `SIGPIPE` on Unix) |
| Windows console close, logoff, shutdown | `watch.stopped` if time allows | — | best effort |
| Broken invariant | … `watch.error` (fatal, `internal_invariant_failure`), `watch.stopped` | empty | 6 |

In text mode, fatal and non-fatal errors go to stderr and the exit codes
are the same. No exit 1: `watch` is not a check. No 3 or 4: it reads no
snapshot.

## 11. Security considerations

- Read-only: `watch` writes nothing but stdout and stderr, runs no external
  process (no Git, even inside a repository) and opens no network
  connection.
- Untrusted kernel data: notification records are parsed with bounds checks
  per record (`NextEntryOffset` chains, name lengths, padding, UTF-16
  surrogates) and fuzzed; names that do not decode are treated as relevant
  and then validated by the existing canonical path rules.
- Links: no handle or descriptor opened below the root follows a link; a
  directory replaced by a link between an observation and its registration
  fails the registration, which marks the watcher dirty.
- Resource exhaustion: a process creating entries as fast as it can costs at
  most one observation per debounce interval (one per maximum delay while
  the activity never pauses), never a growing queue; an idle watcher costs
  one observation per reconciliation interval; registrations are bounded by
  system limits and fail cleanly (`watch_limit_reached`).
- Handles: every exit path, including an expired output grace period,
  closes or abandons to the OS every handle and descriptor; tests count them
  before and after for the in-process paths.
- Privacy: the stream never reveals the absolute root, the host, the user
  or the time. It emits the artifact's structural values as they are (an
  absolute link target that points outside the root, as Diff Result Schema
  v3 does) and the options the user gave (`capture.ignore`). Diagnostic
  messages disclose no local path outside the artifact; tests run with
  roots under recognizable temporary and home paths and check that neither
  appears in any event or message.
- Signals: the `SIGTERM` handler is installed by `watch` only; the other
  commands keep their behavior.
- Terminal safety: text output escapes control characters in paths.

## 12. Cross-platform considerations

- Two test contracts (P1): **structural equivalence** of real runs across
  Linux, Windows, macOS and the native and polling backends, compared at
  quiescent checkpoints after removing `metadata.backend`; and
  **serialization determinism**, proven by goldens built from constructed
  states and generations, byte-identical on every platform.
- Windows: one recursive handle (no per-directory limit), short names and
  attribute notifications handled by the relevance rules, `junction` nodes
  never entered, case-only renames reported as the scanner observes them,
  console close best effort.
- Linux: one watch per directory, bounded by `max_user_watches`; inode reuse
  handled through removal notices; the reference shows how to read and raise
  the limits.
- macOS: one descriptor per directory, bounded by the open-file limit (F8);
  no entry names, so content edits may cost observations; NFD names
  observed as the scanner already normalizes them.
- WSL `/mnt/c`, Docker bind mounts on macOS and Windows, SMB and NFS
  shares: refused in native mode when recognized (decision 8), served by
  `--poll`; when not recognized, reconciliation bounds the delay.
- Process start costs do not apply: `watch` runs no external process.

### 15.2 Properties (real filesystems)

- **Diff equivalence:** seeded random mutation scripts applied step by step:
  each generation's node events equal the comparison of the harness's own
  observations of the two states.
- **Structural equivalence:** the script waits for quiescence at each
  checkpoint; at every checkpoint, each backend and platform reports the
  same fingerprint and node count, and the composition of the generations
  between two checkpoints equals the diff of the checkpoint states. Lines
  are compared after removing `metadata.backend`; the grouping into
  generations is not compared.
- **Convergence:** the last fingerprint equals `app.Fingerprint` with the
  same Capture Semantics.
- **Stream validity:** every stream produced by any test passes the
  validator.

### 15.3 Goldens (serialization determinism)

`testdata/watch/v1/golden/`, produced by the engine with a fake observer,
clock, backend and output from constructed states: started and
generations, moves, `--no-moves`, the three rescan reasons, error recovery,
root removed, startup failure, interrupted, output grace expiry; NDJSON
and text. Byte-identical on the three operating systems. Real filesystem
runs are never compared with goldens byte for byte.

### 15.4 Fuzz

inotify record parser, `FILE_NOTIFY_INFORMATION` parser, relevance path
mapping (Windows relative paths to the structural set), the filesystem
classification, and the stream validator: no panic, strict rejection,
conservative relevance on doubt.

## 21. Explicit non-goals

- Subtree or incremental observation, a persistent state, a cache, a
  database, a daemon or service mode.
- Sockets, HTTP, MCP or any transport other than stdout; several roots.
- Git refs, history, snapshots or `git:` sources in `watch`.
- The initial state as events; timestamps; sequence numbers.
- Content hashing or content events; raw OS events.
- Automatic fallback to polling; waiting for a removed root; a
  user-configurable reconciliation interval in v1.
- Exhaustive classification of network and virtual filesystems; checking
  mount points below the root.
- Atomic publication on stdout; a guaranteed `watch.stopped` after a
  Windows console close.
- FSEvents, cgo, fanotify.
- TUI, Desktop or IDE integration; a stable `watch` (v0.7).
