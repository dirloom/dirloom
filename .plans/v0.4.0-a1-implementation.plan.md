# 2. Décisions normatives a1

Ces décisions doivent guider l'implémentation.

## 2.1 Le fingerprint identifie une vue structurelle

Le fingerprint ne prétend pas nécessairement représenter l'intégralité physique du filesystem.

Il représente :

> **la structure effectivement observable par Dirloom après application des règles structurelles actives.**

Ainsi :

```text
same filesystem
+ different ignore/depth/hidden rules
→ potentially different artifact
→ potentially different fingerprint
```

Mais :

```text
different configuration mechanisms
+ identical resulting artifact
→ identical fingerprint
```

Les options ayant produit l'artefact ne font donc **pas** partie du fingerprint.

Seul le résultat structurel participe à l'identité.

---

## 2.2 La racine est synthétique

Le nom du dossier physique contenant le projet ne doit pas modifier son fingerprint.

Exemple :

```text
/home/alice/project
C:\Users\Bob\source\project-copy
/tmp/test-8471
```

doivent pouvoir produire le même fingerprint s'ils contiennent la même vue structurelle.

La racine canonique est représentée par :

```text
.
```

et non par son chemin absolu ou son basename physique.

---

## 2.3 Les chemins sont relatifs et portables

Tous les chemins canoniques utilisent :

```text
/
```

comme séparateur.

Exemples :

```text
.
src
src/core
src/core/main.go
```

Sont interdits dans un artefact canonique :

```text
C:\project\src
/home/user/project/src
..\src
src\core
```

---

## 2.4 La casse est conservée

Dirloom ne convertit jamais arbitrairement :

```text
Auth
```

en :

```text
auth
```

L'identité est case-sensitive.

Deux noms différents uniquement par la casse restent structurellement distincts dans le modèle canonique.

Si le filesystem local ne peut pas représenter une structure donnée, Dirloom ne doit pas prétendre qu'elle existe.

---

## 2.5 Unicode : NFC

La forme canonique Unicode v1 doit être :

```text
NFC
```

Objectif :

éviter qu'un nom visuellement identique mais encodé différemment entre macOS, Linux ou Git produise arbitrairement deux identités différentes.

Toute normalisation entraînant deux chemins distincts vers le même chemin canonique doit provoquer une erreur explicite de collision.

Dirloom ne doit jamais fusionner silencieusement deux nœuds.

---

## 2.6 Aucun tri dépendant de la locale

L'ordre d'identité ne dépend pas :

* de la langue ;
* de la locale ;
* du filesystem ;
* du terminal ;
* du système d'exploitation.

La projection d'identité doit utiliser un ordre total déterministe défini par Dirloom.

Recommandation normative :

```text
canonical UTF-8 path byte ordering
```

après normalisation canonique.

Le tri utilisé pour le fingerprint n'a pas besoin de modifier le tri visuel existant de Dirloom.

---

## 2.7 Types de nœuds

Le modèle a1 doit au minimum pouvoir représenter explicitement :

```text
directory
regular file
symbolic link
```

et, lorsque déjà exposé par le scanner actuel :

```text
Windows junction
```

Les types spéciaux non supportés ne doivent jamais être silencieusement transformés en fichiers réguliers.

Ils doivent :

* soit disposer d'une représentation canonique documentée ;
* soit provoquer un diagnostic `unsupported node type`.

Ne pas inventer de représentation approximative simplement pour obtenir un hash.

---

## 2.8 Symlinks

Un symlink reste un symlink.

Il ne doit pas devenir l'identité du fichier ou dossier auquel il pointe.

Le fingerprint ne doit pas suivre implicitement sa cible.

La cible logique du lien doit être représentée de manière déterministe lorsque le scanner actuel permet de l'obtenir.

Important :

* ne pas faire dépendre l'identité du `mtime` de la cible ;
* ne pas faire dépendre l'identité de l'existence actuelle d'une cible externe ;
* ne pas transformer un symlink cassé en erreur uniquement parce que sa cible n'existe plus ;
* ne pas résoudre récursivement le contenu de la cible.

Une cible interne absolue pouvant être exprimée relativement à la racine doit être canonicalisée sous forme root-relative afin qu'un déplacement du repository ne modifie pas arbitrairement le fingerprint.

La sémantique exacte doit être spécifiée dans le contrat d'identité.

---

## 2.9 Métadonnées exclues

Identity Projection v1 exclut au minimum :

```text
mtime
ctime
atime
owner
uid
gid
ACL
platform-specific permissions
absolute root
hostname
username
capture timestamp
terminal
TTY
theme
colors
icons
presentation styles
output indentation
```

Le bit executable ne doit pas être ajouté implicitement à a1 uniquement parce que Git le connaît.

Une extension future pourra modifier la projection via une **nouvelle identity version**, pas en changeant silencieusement `v1`.

```go

    Name     string
    Kind     NodeKind
```

---

## 6.2 Root

Le root canonique :

```text
Path = "."
```

Son nom physique ne participe pas à l'identité.

Si le modèle doit conserver un display/source label, celui-ci doit être explicitement extérieur à Identity Projection v1.

---

## 6.3 NodeKind

Créer une enum/type fermé plutôt que des chaînes dispersées.

Exemple conceptuel :

```text
directory
file
symlink
junction
```

Sa représentation dans l'encoding doit être stable et indépendante des valeurs accidentelles d'un `iota` susceptible d'être réordonné plus tard.

---

## 6.4 Validation interne

L'Artifact doit pouvoir être validé indépendamment du filesystem.

Invariants :

```text
exactly one root
root path == "."
no absolute path
no path escaping root
no backslash canonical separator
no duplicate canonical path
name compatible with path
parent exists
node kinds valid
children belong to parent
no canonical Unicode collision
```

---

## 6.5 Aucune information présentationnelle

```text
identity → terminal
```

## 6.6 Immutabilité logique

Après canonicalisation, le moteur d'identité doit considérer l'artefact comme immuable.

# 7. LOT 3 — Canonicalisation des chemins

## Objectif

Garantir que deux observations logiquement identiques produisent les mêmes identités.

---

## 7.1 API dédiée

Ne pas éparpiller :

```go
strings.ReplaceAll(...)
filepath.Clean(...)
```

dans plusieurs packages.

Créer un point unique responsable de :

```text
native path
→ canonical Dirloom path
```

---

## 7.2 Relative paths

Les chemins doivent être calculés relativement à la racine source.

Le chemin absolu ne doit jamais entrer dans Identity Projection.

---

## 7.3 Separator

Conversion :

```text
native separator
→ /
```

doit se faire avec connaissance de la plateforme/source.

Ne pas traiter aveuglément `\` comme séparateur dans une chaîne POSIX où il peut constituer un caractère valide.

---

## 7.4 Dot segments

Normaliser lexicalement les segments appropriés.

Refuser toute canonicalisation conduisant hors de la racine.

---

## 7.5 Unicode NFC

Utiliser une implémentation Unicode fiable.

Pour Go, si nécessaire :

```text
golang.org/x/text/unicode/norm
```

est acceptable si cette dépendance est réellement nécessaire.

Ne pas écrire un normaliseur Unicode artisanal.

---

## 7.6 Collision detection

Cas obligatoire :

```text
raw path A
raw path B

NFC(A) == NFC(B)
```

doit produire :

```text
canonical path collision
```

avec diagnostic identifiant les deux entrées concernées.

---

## 7.7 Case

Ne jamais appeler :

```text
strings.ToLower
strings.EqualFold
```

pour construire l'identité.

---

# 9. LOT 5 — Identity Projection v1

## Objectif

Créer une représentation spécifiquement conçue pour définir l'identité.

---

## 9.1 Séparation Artifact / Identity

Ne jamais faire :

```text
Artifact struct
= forever fingerprint contract
```

Créer une projection explicite :

```text
Artifact
   ↓
ProjectIdentityV1(...)
   ↓
Identity Records
```

Ainsi, a2 pourra ajouter des métadonnées de snapshot sans modifier le fingerprint.

---

## 9.2 Flattening déterministe

Même si Artifact est hiérarchique, Identity Projection peut produire :

```text
ordered node records
```

triés selon le contrat canonique.

Cela rend le hash indépendant de l'ordre accidentel des slices en amont.

---

## 9.3 Record minimal

Chaque record v1 doit contenir uniquement les données nécessaires.

Conceptuellement :

```text
canonical path
node kind
kind-specific deterministic attributes
```

Ne pas ajouter :

```text
mtime
size
owner
theme role
icon
source absolute path
scanner index
memory address
capture timestamp
```

---

## 9.4 Name

Comme `name` est dérivable du canonical path pour les non-root nodes, décider explicitement s'il est :

* validé mais non sérialisé ;
* ou sérialisé.

Éviter les informations redondantes dans l'identité lorsque celles-ci peuvent diverger.

Recommandation :

> valider `Name`, mais utiliser le chemin canonique comme vérité d'identité.

---

## 9.5 Symlink identity

Encoder explicitement le fait que le node est un lien.

Si la cible fait partie du contrat choisi, son encoding doit respecter les règles définies en L1.

Ne jamais incorporer le contenu de la cible.

# 11. LOT 7 — Fingerprint Engine

## Objectif

Créer la primitive métier produisant :

```text
dlm:v1:sha256:<digest>
```

---

## 11.1 Fingerprint type

Créer un type interne fort plutôt qu'une simple chaîne dispersée.

Conceptuellement :

```go
type Fingerprint struct {
    Version   IdentityVersion
    Algorithm Algorithm
    Digest    [32]byte
}
```

---

## 11.2 Formatter

Format exact :

```text
dlm:v1:sha256:<lowercase-hex>
```

Le digest :

* doit être complet ;
* ne doit pas être tronqué dans le contrat canonique ;
* utilise hexadecimal lowercase.
