# Dirloom v0.4.0-a7 structural history benchmarks

Local measurements of `dirloom history` without the command-line layer: one
Git session, the first-parent walk, every commit and tree read through one
`git cat-file --batch` process, Identity Projection v1, Fingerprint v1 and a
comparison per commit. They are compared with the same summaries obtained
from separate comparisons of `git:<parent>` and `git:<commit>`, as repeated
`dirloom diff` runs would compute them. Times are not CI gates. The
architectural argument for linear cost is in
[Structural History v1](../contracts/structural-history-v1.md#complexity);
these numbers confirm it empirically and do not replace it.

## Command

```bash
go test ./internal/history -bench BenchmarkHistory -benchtime=1x -count=5 -run '^$'
```

Each value is the median of the 5 runs. Runs of the same case stayed within
24% of each other (within 12% from 10,000 entries on); allocations and
allocated bytes varied by less than 0.3%, retained bytes by less than 5%.

## Fixtures

One repository per shape, built once per test binary with `git fast-import`
and never checked out: a first commit with `src/m<i>/f<j>.go` (modules of
nine files, about `entries` paths) and `README.md`, then commits that each
add one file, delete one file in another module and, every fifth commit,
rewrite `README.md` (a contents-only change). The walk and diff fixtures have
101 commits; the retained-memory fixture has 1,001. Every case asserts its
entry count or that each compared pair changed.

| Case | What runs |
| --- | --- |
| `HistoryWalk` | `history.Walk` with `--limit` commits: resolution, the shallow list, one batch process, `limit + 1` commits and trees, projections, fingerprints, `limit` comparisons with `structural-v1` |
| `HistoryVersusDiff` | 20 calls of `comparison.Compare(git:HEAD~k+1, git:HEAD~k)`: each opens two Git sessions and observes two trees |
| `HistoryRetainedEntries` | the heap still held after a walk, per listed entry, with the result kept alive |

## Reading the results

**One session instead of one per tree.** Twenty separate comparisons cost
about 9.8 s at 1,000 and at 10,000 entries alike: they open 40 Git sessions,
and process starts dominate. The history of the same 20 commits opens one
session and costs 277 ms at 1,000 entries (36 times less) and 687 ms at
10,000 (14 times less).

**The initial target is met.** The framing review set 20 commits over a
10,000-entry tree within 2 s on Windows as an initial target: the median is
0.69 s. No optimization lot is needed.

**The cost is linear in commits times tree size.** From 20 to 100 commits,
the walk adds about 3.3 ms per commit at 1,000 entries and 22 ms per commit
at 10,000. Allocated bytes grow 4.5 and 4.8 times for 5 times the commits,
and 9 times from 10,000 to 100,000 entries at 20 commits. The fixed cost of
resolution and the batch process is about 0.2 s, as in A6.

**Allocation is transient; retention is small.** A walk allocates about
15 MB per commit at 10,000 entries, but it keeps only two observations at a
time, so that memory is collected as the walk advances. What a finished
history retains is its entries: about 290 bytes each, plus about 20 KB that
do not depend on the limit (482 bytes per entry at `--limit 100`, 311 at
`--limit 1000`, about 0.3 MB in all).

## Scope

These numbers cover one platform. The separate comparisons run in process;
twenty real `dirloom diff` invocations would also pay twenty process starts
of `dirloom` itself. There is no cache: repeated runs cost the same.
