# Dirloom v0.4.0-a8 structural watch benchmarks

Measurements of `dirloom watch` without the command-line layer: the engine,
the native backends and the polling backend, observing real trees on the
local machine and on the three CI runners. They check the initial targets
of the implementation plan (§16) and set the reconciliation interval of
[Structural Watch v1](../contracts/structural-watch-v1.md#reconciliation).
Times are not CI gates, and none of these numbers is a contract.

## Command

```bash
go test ./internal/app -run '^$' -bench BenchmarkWatch -benchtime=1x -timeout 55m
```

Each benchmark runs once and takes its own five samples where the plan asks
for a median; the tables give the median and, in brackets, the largest
sample. Across the five samples of a case, the largest stayed within 3% of
the median for the signal latency, within 9% for the observations of
100,001 nodes, within 31% for those of 10,001 nodes (a few milliseconds)
and within 17% for the startup. The idle and content windows can be shortened
with `DIRLOOM_BENCH_IDLE`, `DIRLOOM_BENCH_POLL` and `DIRLOOM_BENCH_CONTENT`;
every number below uses the full windows.

## Fixtures

The trees are the synthetic trees of the fingerprint benchmarks: 20
directories of empty files, 10,001 or 100,001 nodes with the root. The
startup case uses 100 directories of 100 directories (10,101 nodes, all
directories). Capture Semantics: default ignores and `.gitignore` files on,
as `dirloom watch` uses them; the native cases use the default debounce
(200 ms) and the 60 s reconciliation unless said otherwise.

| Case | What runs |
| --- | --- |
| `WatchSignalToState` | a native watch of 10,001 nodes; one directory created, until its `state.changed` is published; after each sample, the verification observation of the new registration |
| `WatchObservation` | one observation as a reconciliation makes it (scan, Identity Projection v1, Fingerprint v1), and a full rescan (the observation and its comparison with the last state) |
| `WatchContentWrites` | a native watch of 10,001 nodes while 100 files are appended to, truncated, rewritten, `chmod`-ed and touched in turn for 60 s, with the reconciliation pushed beyond the window; the observations they cause are counted, and any structural event fails the case |
| `WatchSlowConsumer` | a native watch of 10,001 nodes whose consumer stops reading while a generation waits and 1,000 or 10,000 entries are created and removed; then it reads again; the heap in use is sampled every 2 ms during the catch-up |
| `WatchStartup` | the start of a native watch of 10,101 directories, until `watch.started` (after the registrations on Linux and macOS) |
| `WatchIdleNative` | a native watch of 10,001 nodes left idle for 10 minutes: process CPU time and observations |
| `WatchIdlePoll` | `--poll 2s` on the same idle tree for 2 minutes |

## Reading the results

**Every initial target is met; no subtree re-observation is proposed.** The
signal latency is the debounce plus 22 to 68 ms, within the 450 ms target on
the four machines. A full rescan of 100,001 nodes takes 0.22 to 0.43 s, a
fifth of the 2 s target or less. The plan's fallback, subtree
re-observation (Q2), is therefore not proposed.

**Content edits cost nothing.** Between 320,000 and 1,960,000 content-only
writes in a minute caused no observation on any backend, Windows included,
where hidden entries are excluded and each attribute record is ruled out
with one attribute read (§5.5). This is the zero-observation property that
the backend tests prove by event order (LOTS 4–6), measured end to end.

**A slow consumer does not grow the heap.** While a generation waits for
the consumer, the engine does not observe: it only keeps the backend's
flags. When the consumer reads again, one observation reaches the final
state. The peak heap of that catch-up stayed at or below the steady heap of
the running watch (0.85 to 1.00 times), and 10,000 changes cost no more than
1,000. The heap is the test process's, sampled every 2 ms: a shorter peak
may be missed, and the bound is far from the 3× target.

**Startup.** On Linux and macOS a native watch of 10,101 directories
registers each of them before `watch.started`: 153 ms and 450 ms, within the
1 s target. Windows registers nothing (one recursive handle); its startup is
the observation of 10,101 directories, which listing directories on NTFS
makes slower: 694 ms on the runner, 1.08 s locally.

**The reconciliation interval stays at 60 s.** An idle native watch of
10,001 nodes made 9 observations in 10 minutes (one per interval, which
restarts after each observation) and used 0.07% to 0.13% of one core. At
100,001 nodes, one reconciliation costs 0.22 to 0.43 s, about 0.4% to 0.7%
of one core at 60 s. A shorter interval would multiply that cost to recover
faster from a missed notification, which the backends made rare: the LOT 8
matrix needed no reconciliation rescan. A longer one would delay that
recovery, and on Linux and macOS the detection of a renamed ancestor of the
root, which only the identity check of an observation sees. Structural
Watch v1 keeps 60 s; it is the value set by these figures.

**Polling costs more than notifications.** `--poll 2s` on the same idle tree
uses 1.5% to 3.8% of one core, 12 to 37 times the native watch: it observes
the whole tree every 2 s instead of once a minute. Polling remains the
choice for the filesystems that native mode refuses.

## Scope

These numbers cover empty files and in-process watches: a scan reads
metadata, never contents, so file sizes do not change them, but deeper or
wider trees, network filesystems and antivirus scanning do. The CI runners
are shared virtual machines. Memory is the Go heap in use, not the
resident set. The latency starts when the test creates the directory, so it
includes the backend's delivery of the notification. A Windows console
close and the memory of a real terminal consumer are not measured.
