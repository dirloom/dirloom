# Dirloom v0.4.0-rc1 performance and memory baselines

> **Status:** the record of LOT 6 of the v0.4.0-rc1 plan, for decisions D6 and D8. These are measurements on one reference machine. They are not CI gates and not contracts.
>
> They are versioned baselines:
> - [`tools/perfbaseline`](../../tools/perfbaseline) generates the fixtures and reruns every scenario;
> - [`v0.4-rc1/`](v0.4-rc1/) keeps every run.

## Summary for the CTO review

This section prepares the arbitration of the resource limits. It does not choose.

**What was measured.**

- 37 complete workflows, the critical and high scenarios of the LOT 6 framing (§3.4 of the plan).
- Each ran 5 times, in fresh processes, in a Windows job limited to 8 GiB.
- The heap, the process memory, the allocations and the time are kept apart, and for `watch`, the convergence.
- Then smaller budgets and `GOMEMLIMIT`, and the alpha benchmarks rerun against their published values.
- 1 h 43 for the campaign; about 2 hours of follow-ups.

**8 GiB holds everywhere.** No run came near the 8 GiB job:

- the highest valid workflow committed 3.4 GiB: two 252 MiB snapshots compared, at the node and byte limits;
- the highest of all committed 4.1 GiB: a hostile 250 MiB object read after a valid 2,000,000-node snapshot, then refused.

**Where it breaks.** The budgets below are what Dirloom can commit, on a machine whose system and programs already use the rest.

| Memory available to Dirloom | What still runs at the 2,000,000-node limit |
| --- | --- |
| 4 GiB | every valid workflow; the hostile case fails 3 runs out of 5 |
| 3 GiB | two snapshots compared, except the long-named pair, which failed once in 5; the hostile case always fails |
| 2 GiB | loading or writing one snapshot, and the Git diff. Verifying one against a live tree passes 4 runs out of 5, and `diff snapshot: live:` 2 out of 5. Comparing two snapshots always fails |
| 2 GiB with `GOMEMLIMIT=1792MiB` | two snapshots compared, wide and long-named, 5 out of 5, for at most 6% more time |

A run that exceeds its budget stops with `fatal error: out of memory`, without a Dirloom diagnostic. On Windows, under a job limit, the Go process then hangs until something kills it. A plain Go program does the same.

**The cost of each limit** is tabulated in §[Cost of each limit](#cost-of-each-limit).

- **Snapshot bytes (256 MiB).** It bounds the worst case: the hostile object (3.4 GiB alone, 4.1 GiB after a 2,000,000-node snapshot), and the valid long-named pair (up to 3.4 GiB).
- **Snapshot nodes (2,000,000).** About 1.3 GiB per million nodes for two snapshots compared (2.7 GiB at the limit), and 0.9 GiB per million for one snapshot loaded or verified.
- **Nesting, ignore patterns and Git limits.** Nesting refuses at once. The Git node limit refuses the bomb in 0.6 s. The Git path limit costs 1.7 GiB at its edge.
- **The two pattern limits cost time, not memory.** Time grows with patterns × entries:
  - 4,096 `capture.ignore` patterns: 35 s for 100,000 nodes;
  - a `.gitignore` at the 1 MiB limit: 212 s for 100,000 nodes. Git itself takes 88 to 126 s there.

**Options for the node limit.** For the CTO to choose; none is recommended here.

| Option | What the measurements say |
| --- | --- |
| A. Keep 2,000,000 | Every workflow fits 4.1 GiB, and every valid one 3.4 GiB. A machine with 8 GiB of RAM must leave Dirloom that much. Below 3 GiB available, the largest comparisons start to fail |
| B. Lower it, for example to 1,000,000 | Two snapshots compared stay under 1.5 GiB (measured at 1,000,000). The hostile worst case does not drop: it is set by the byte limit, 3.4 GiB alone. Trees and Git trees above 1,000,000 nodes could no longer be snapshotted or observed |
| C. Keep 2,000,000, and set a Go memory limit in Dirloom (`debug.SetMemoryLimit`) | Measured only through the environment: in 2 GiB, both comparisons at the limit then pass, for at most 6% more time. It cannot go below the live heap, 1.3 to 2.4 GiB at the limits. Choosing its value, fixed or from the machine, is a design decision. Dirloom code changes, so the CTO decides |
| D. Keep 2,000,000, and document the memory needed | No code change. LOT 7 would publish the figures (about 1.3 GiB per million nodes for a comparison, up to 4.1 GiB at the limits), and that users can set `GOMEMLIMIT` themselves |
| E. Lower the byte limit too | It would lower the hostile case, which scales with the document. But a valid 2,000,000-node snapshot takes 156 to 252 MiB, so a lower byte limit also lowers the node limit in practice |

The options combine: for example A or B with D.

**Other findings.**

- **D8:**
  - the reference machine and the investigation threshold are now fixed (reservation R4, §7 of the plan);
  - the first comparison of the alpha baselines found two time deviations above 20%, and investigated both;
  - no code regression: one deviation is Go 1.26.10 against Go 1.27.2, the other the state of the machine (§[Alpha benchmarks rerun](#alpha-benchmarks-rerun)).
- **The release toolchain.** With Go 1.26.10, the toolchain of `go.mod`, loading a snapshot takes about 48% more time than with Go 1.27.2. The peak heap is the same. The toolchain is outside LOT 6; this is only a measurement.
- **`watch`.** 95 bursts of about 800 operations over 100,000 nodes all converged: median 518 ms, maximum 805 ms. There was no error and no rescan, and the retained heap stayed flat over 5 minutes.
- **The snapshot writer.** It refuses more than 2,000,000 nodes and 256 MiB, so `dirloom snapshot` of a larger tree fails. A live observation has no node limit.
- **No engine change was made and no limit was touched.** The only code added is the measurement tool.

## Method

### Complete workflows

Each run is a fresh process of `tools/perfbaseline`. It calls `cli.Execute(ctx, args, stdout, stderr, version)`, the function that `cmd/dirloom` calls, with the arguments of one `dirloom` command line. Consequences:

- every layer runs: flag parsing, configuration, snapshot reading, scanning, Git, the comparison, move detection, rendering;
- `git:` sources start the real `git` processes;
- stdout is counted and discarded: its size is recorded, not its write time to a terminal or a file.

A `dirloom` process would add only its own start, a few milliseconds.

`watch` runs the same way, with the tool changing the watched tree (§[A long watch](#a-long-watch-with-bursts-of-changes-high)).

### Measures

Each measure is kept apart:

| Measure | Definition |
| --- | --- |
| Time | wall time of `cli.Execute` in the process; the process wall time and its CPU time are also recorded |
| Go heap peak | highest `/memory/classes/heap/objects:bytes` (the `HeapAlloc` of `runtime.MemStats`: live objects and garbage not yet swept), read every 1 ms through `runtime/metrics`, which does not stop the world |
| Live heap peak | highest `/gc/heap/live:bytes`: the heap that the last finished collection marked live |
| Allocations | `TotalAlloc` and `Mallocs` over the workflow, the definitions of `go test -benchmem` |
| Process commit peak | `PeakPagefileUsage` of the process: the private memory it committed at its peak. A memory limit counts this |
| Working set peak | `PeakWorkingSetSize`: the peak resident memory, which depends on the free RAM |
| Job commit peak | `PeakJobMemoryUsed` of the process's job: Dirloom and the `git` processes it starts |
| Watch convergence | from the creation of a burst's last file to the arrival of the `state.changed` that adds it |

The runner reads the process counters after the process exits, through a handle opened when it started, so a failed run keeps its peaks.

### Runs

- Each scenario runs **5 times**, each in a new process. Tables give the median, then the minimum and the maximum.
- A run counts only if its exit status and the start of its output match the scenario: for example, exit 3 with `snapshot_limit_exceeded`.
- Every failed run is listed in the results.

### The 8 GiB environment

WSL2 and Docker are not installed on this host. The 8 GiB environment is a **Windows job object**:

- `JOB_OBJECT_LIMIT_JOB_MEMORY` caps at 8 GiB the memory that the measured process and its `git` processes can commit together;
- beyond it, an allocation fails, and Go stops with `fatal error: out of memory`;
- the runner starts the process, puts it in the job, and only then lets it run (it waits for a line on stdin).

The job caps commit, not RAM. A real 8 GiB machine differs in two ways:

- **the operating system and the other programs** take part of that memory;
- **paging** lets a process use more than the RAM, slowly, up to the system commit limit.

A run that fits the job commits less than 8 GiB, and would fit in 8 GiB of RAM only if nothing else needed it.

**A Go process that runs out of memory in a job does not exit.** Under the job limit, Go writes:

```text
runtime: VirtualAlloc of 8192 bytes failed with errno=1455
fatal error: out of memory
```

It then prints its traceback, but the process was still alive 60 s later, until something killed it.

- A plain Go program does the same: standard library only, Go 1.26.10, a 100 MiB job, allocating until it fails.
- So this comes from the Go runtime on Windows, not from Dirloom.
- The runner ends the job 5 s after the fatal error appears. It records the run as out of memory, with its time to the failure.

The effect on users: on Windows, a `dirloom` process under a commit limit (a job object or a Windows container) can hang after `fatal error: out of memory` instead of exiting with status 2. Without such a limit, Windows pages before it refuses memory. This was not measured: it would page the shared machine.

### Fixtures

`perfbaseline gen` writes every input under one directory. They are deterministic, which these checks confirm:

- the snapshot that `dirloom snapshot` writes of a generated tree has the same SHA-256 as the document generated in memory for the same shape (100,000 and 2,000,000 nodes);
- the Git repositories have fixed identities and dates, so their commit ids are reproducible.

The checksums and commit ids are in [`fixtures.json`](v0.4-rc1/fixtures.json).

**The wide shape** is the shape of the [snapshot limit measurements](v0.4-rc1-snapshot-limits.md), so the two records compare:

- directories `d00000`, `d00001`, ... of up to 1,000 empty files `file-000000.txt`, ...;
- an empty directory `zz-moved`;
- about 82 bytes per node in a snapshot document.

Node counts always include the root and the directories.

| Fixture | Contents |
| --- | --- |
| `snap-wide-100k`, `snap-wide-1m`, `snap-wide-2m` | snapshot documents of 100,000, 1,000,000 and 2,000,000 nodes (7.8, 78 and 156 MiB). `a` is the wide shape. `b10` moves every 10th directory under `zz-moved` (10% of the nodes); `b50` moves every 2nd. The node count is unchanged, and each moved directory keeps a unique name, so Move Detection `structural-v1` pairs it |
| `snap-long-2m` | the same at 2,000,000 nodes with 50 more bytes in each file name: `a` is 251.7 MiB, `b10` 253.4 MiB. These are the most expensive valid documents within both the byte and the node limits, as in the snapshot limit measurements |
| `bad/keys.json` | 250 MiB holding one JSON object of 17.5 million unique keys: finding F6 of the LOT 5 audit |
| `bad/nodes-over.json` | the `a` document of 2,000,000 nodes with one more node in its array, edited as text: Dirloom refuses to write a snapshot that it would refuse to read |
| `bad/bytes-over.json` | the valid long document followed by spaces up to 271 MiB, edited as text for the same reason |
| `bad/nesting.json` | 3,000,000 nested JSON arrays, 6 MB |
| `bad/ignore-4096.json` | a valid snapshot of an empty directory whose `capture.ignore` holds 4,096 patterns, the limit; none matches a generated entry |
| `live-wide-100k`, `live-wide-1m`, `live-wide-2m` | the wide shape on disk: 100,000, 1,000,000 and 2,000,000 nodes of empty files |
| `live-deep-100k` | 100 chains of 50 nested directories, each directory holding 19 empty files: 100,001 nodes in 5,001 directories, paths up to 106 bytes |
| `live-gi-short` | 99,999 wide nodes and a root `.gitignore` of 1,048,567 bytes: 80,659 short patterns (`*.ext000000`, `gen000001/`, `**/tmp000002/**`, `/build000003`, ...), none of which matches |
| `live-gi-long`, `live-gi-wild` | the same tree under a `.gitignore` of 16 lines of 65,000 bytes, below the 65,535-byte line limit. `long` lines are literal; `wild` lines alternate `*` and a letter |

### Reproduce

```sh
GOTOOLCHAIN=go1.26.10 go build -o perfbaseline.exe ./tools/perfbaseline
./perfbaseline.exe gen -fixtures F
./perfbaseline.exe run -fixtures F -out results.jsonl -runs 5 -mem-limit 8GiB -label 8gib
./perfbaseline.exe summarize results.jsonl
./perfbaseline.exe compare -base docs/benchmarks/v0.4-rc1/results-8gib.jsonl -base-label 8gib -new results.jsonl -new-label 8gib
```

- Generating the fixtures takes about 10 minutes and about 9 GiB of disk, most of it the trees of empty files.
- The campaign takes about 2 hours.
- `-scenarios <regexp>` and `-runs` select a subset.
- `perfbaseline list` prints every scenario with its command line.

- **Two snapshots of 2,000,000 nodes: 2.7 GiB of commit and 45 to 53 s.** The commit grows linearly with the nodes, about 1.3 GiB per million:
  - 0.18 GiB at 100,000 nodes;
  - 1.4 GiB at 1,000,000;
  - 2.7 GiB at 2,000,000.
- **Two long-named documents of 252 MiB** give the highest valid run measured, 3.4 GiB (median 2.5 GiB). Their live heap is the highest of the valid diffs, 1.4 GiB.
- **Reading the snapshots dominates.** At 2,000,000 nodes:
  - loading one document alone takes 20 s and allocates 10.6 GiB (`load-2m`);
  - a diff loads two, then compares: 23.8 GiB allocated, in 505 million allocations;
  - the same trees observed from Git compare in 11 s (`gitdiff-2m`).
- **Move detection costs little at this scale.** On the same documents, detection changes neither the commit nor, beyond the noise, the time, and adds 2% to 4% of allocated bytes:
  - 10% of directories moved: 24,408 MiB allocated with detection, 23,880 MiB without;
  - 50% moved: detection allocates less (25,552 MiB against 26,769 MiB), because 1,000 `MOVED` changes replace 2,000,000 `ADDED` and `REMOVED` ones.
- **The output does not raise the peak.** Without detection, 50% moved writes 257 MiB of JSON, which the encoder builds in memory before it writes it. The commit is the same as with detection: the peak comes earlier, while the documents are read.
- **The heap peak is about twice the live heap.** At 2,000,000 nodes, collections keep 1.3 GiB live. The heap in use reaches 1.8 to 2.7 GiB, depending on when a collection starts (`GOGC=100`), and the commit follows it. This explains most of the spread between runs.

- **The F6 document is the most expensive input measured.**
  - **Alone:** `verify` reads the 250 MiB object of 17.5 million unique keys, then refuses it (`INVALID_SNAPSHOT`, `missing_snapshot_field`, exit 3). It takes 55 s, a heap peak of 2.7 GiB and 3.4 GiB of commit. LOT 5 measured 2,510 MiB of heap in process; the CLI workflow adds 11%.
  - **After a valid 2,000,000-node snapshot**, as side B of a `diff`, it is the highest run of the whole campaign: 77 s, 3.8 GiB of commit at the median and 4.1 GiB at the most.

- **The other limits refuse before most of the cost:**
  - 2,000,001 nodes in 1.7 s and 0.47 GiB, when the array exceeds the node limit;

  - 3,000,000 nested arrays in 0.03 s.
- **4,096 `capture.ignore` patterns cost time, not memory.** Verifying 100,000 live nodes takes 35 s instead of 0.8 s, with the same memory. - **A `.gitignore` at the 1 MiB limit costs time, not memory.** Fingerprinting 100,000 nodes:
  - under 80,659 short patterns: 212 s (151 to 277 s), for 125 MiB of commit;
  - under 16 lines of 65,000 bytes: 0.22 s.

  The pattern count costs, not the line length: the dependency tests each path against every pattern until one matches, and here none does. Git takes the same order of time:
  - `git ls-files --others --exclude-standard` (Git 2.56.1) lists the same tree in 88 s and 126 s, 2 runs outside the campaign;
  - without the file, it takes 0.6 s.

  At 2,000,000 nodes the 1 MiB limit would allow about 70 minutes: an extrapolation, not measured.

  - **4 GiB:** every valid workflow passes. The F6 document after a 2,000,000-node snapshot fails 3 runs out of 5.
  - **3 GiB:**
    - two wide snapshots of 2,000,000 nodes still compare;
    - the long-named pair failed once in 5;
    - the F6 case always fails.
  - **2 GiB:**
    - comparing two snapshots of 2,000,000 nodes fails every time;
    - loading or writing such a snapshot, the Git diff and the Git chain still pass;
    - `verify`, `diff snapshot: live:` and `diff snapshot: git:` at 2,000,000 nodes pass only 2 to 4 runs out of 5.

    - wide diff: 45.8 s against 47.3 s;
    - long diff: 66.6 s against 62.7 s (+6%);
    - F6 case: 78.5 s against 76.5 s in the 8 GiB campaign (+3%).

  - Only these three cases were measured with it.

## Investigation threshold (D8)

**The rule.**

- To compare a later build with these baselines, rerun the same campaign on the reference machine, then compare it with the committed results:

  ```sh
  perfbaseline compare -base docs/benchmarks/v0.4-rc1/results-8gib.jsonl -base-label 8gib -new results.jsonl -new-label 8gib
  ```

- `compare` takes each scenario's median of time, allocated bytes, Go heap peak and process commit peak. It flags every change of **20% or more**.
- A flag starts a **manual investigation**, never an automatic rejection.
- No time threshold runs in CI, and shared runners never fail on time.

**How much each measure varies.** Over the 5 runs of each scenario of this campaign, the largest deviation from the median was:

| Measure | Typical scenario (median) | Worst scenario | What a 20% change means |
| --- | ---: | ---: | --- |
| Allocated bytes | under 0.1% | 0.4% | the code changed: these are deterministic |
| Allocations | under 0.1% | 1.1% | the same |
| Process commit peak | 5% | 36% | rerun first: the peak depends on when collections start |
| Go heap peak | 10% | 48% | the same |
| Time | 19% | 173%, sub-second scenarios whose first run is cold | rerun on an idle machine first |

**The first application of the threshold** is to the alpha baselines, rerun below. It found time deviations above 20% in two of them, a5 and the snapshot load, and investigated both.

## Scope

**What these numbers do not cover:**

- **One machine, under load.** Times are those of a busy laptop. Linux, macOS and the CI runners were not measured.
- **The Windows job caps commit, not RAM.** A real 8 GiB machine also holds the system and other programs, and pages before it refuses memory. Paging was not measured: it would have paged the shared machine.
- **The output's destination.** stdout is counted, not written to a terminal or a file.
- **Generated shapes, not real repositories.** Wide trees of empty files, deep chains, the a7 history shape. Real repositories mix them, and the RC soak (§5.1 of the plan) records real ones.
- **The live trees are cold or warm as the campaign left them.** The first run of a sub-second scenario is often the slowest.
- **Not measured:**
  - a live tree, or a `dirloom snapshot`, above 2,000,000 nodes;
  - `watch` with `--poll`, or a watch of 2,000,000 nodes;
  - the `requiredFeatures` limit;
  - the effect of antivirus scanning, beyond its being on.
