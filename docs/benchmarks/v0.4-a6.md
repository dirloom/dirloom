# Dirloom v0.4.0-a6 Git source benchmarks

Local measurements of one Git source observation: revision resolution, the
on-demand tree reads through `git cat-file --batch`, tree parsing, the
scanner and artifact construction. They are compared with a filesystem
observation of a checkout of the same commit under the same capture. Times
are not CI gates. The architectural argument for linear cost is in
[Git Tree Source v1](../contracts/git-tree-source-v1.md#complexity); these
numbers confirm it empirically and do not replace it.

## Command

```bash
go test ./internal/source -bench BenchmarkObserveGitTree -benchtime=5x -count=5 -run '^$'
```

Each value is the median of the 5 runs. Runs of the same case stayed within
13% of each other for every Git case, and within 24% for the filesystem
cases (16% and 17% at 1,000 and 10,000 entries, 24% at 100,000).

## Fixture

One repository per size, built once per test binary with `git fast-import`
(one blob reused by every file) and checked out with `git reset --hard`:
`src/m<i>/f<j>.go`, modules of nine files, so `entries/10` module trees and
`entries` tree entries in all. Each case asserts the node count of its
artifact on every iteration.

| Case | What runs |
| --- | --- |
| `resolve` | `gitsource.NewRunner` and `Resolve("HEAD")`: four `git` processes (`rev-parse --show-object-format`, `rev-parse --verify`, `cat-file -t`, `rev-parse <commit>^{tree}`). The `git version` check is cached per process and runs once for the whole benchmark |
| `git` | `source.Git.Observe` on `HEAD`: resolution, one `cat-file --batch` process, every tree read and parsed, scanner, `FromTree` |
| `filesystem` | `source.Filesystem.Observe` on the checkout: the same scanner over the operating-system filesystem, then `FromTree` |
| `git-depth-1` | `source.Git.Observe` with depth 1: the root tree is read; `src` is listed and never read |

`git` and `filesystem` use the same capture: default ignores (which drop the
checkout's `.git`) and hidden entries included, so both artifacts have the
same `entries + 2` nodes.

## Reading the results

**A fixed cost of process starts.** `git-depth-1` costs 218 to 223 ms at
every size, of which resolution is 170 to 194 ms: four `git` processes, so
roughly 45 ms per process start on this machine. Starting and closing the
batch process adds 30 to 55 ms more. At 1,000 and 10,000 entries this fixed cost dominates,
and a filesystem observation of the checkout is faster. A `dirloom diff`
of two revisions pays it twice, plus one `git version` check.

**Excluded subtrees cost nothing.** `git-depth-1` has the same time and
the same 2,401 allocations at 1,000, 10,000 and 100,000 entries: the module
trees it excludes are never read.

**The variable cost is linear and below the filesystem's.** Above the
fixed cost (`git` minus `git-depth-1`), reading and parsing every tree costs
about 7 ms at 10,000 entries and 99 ms at 100,000. From 10,000 to 100,000
entries, allocations grow 9.8 times and allocated bytes 9.1 times. At
100,000 entries the whole Git observation (321 ms) is less than half of the
filesystem observation of the checkout (744 ms), and allocates 16% fewer
bytes.

## Scope

These numbers cover one platform. Process starts are usually much cheaper
on Linux and macOS, where the fixed cost should shrink accordingly; this
was not measured here. Resolution uses the commands listed in Git Tree
Source v1, one process each; reducing that count would change the
contract's command list and is not part of v0.4.0-a6.
