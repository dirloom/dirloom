# v0.4.0-rc1 soak protocol (D14)

> **Status:** validated by the CTO on 2026-11-28 (plan §3.6); the soak has not started. It starts after the publication of `v0.4.0-rc1` (G6), on an explicit G7 GO, and its report closes gate G7 with the CTO's `v0.4.0` decision. It formalizes §5.1 of the [plan](../../.plans/v0.4.0-rc1-implementation-plan.md) and roadmap §12.15. Reservation R5 stays open until the repositories and machines are [qualified](#inputs-from-the-cto).

The soak is real use of the published release candidate on real repositories, before `v0.4.0`. It looks for what the tests, the benchmarks and the acceptance packs cannot find.

## Inputs from the CTO

Decided on 2026-11-28:

1. **The soak owner:** the repository owner, assisted by the agents. The owner keeps the report and opens the incidents.
2. **The start:** after G6, on an explicit G7 GO.

Still to qualify, when the CTO asks for it (R5 stays open until then):

3. **One repository for each of the seven profiles,** with its measured SHA, checked against the profile's definition below. A repository may serve two profiles only if it meets both definitions. The candidates, not qualified yet:

   | Profile | Candidate |
   | --- | --- |
   | P1 small Go CLI | Dirloom |
   | P2 TypeScript monorepo | a real TypeScript monorepo, to name |
   | P3 Flutter project | Sonora |
   | P4 large repository | LLVM, or another repository of at least 100,000 nodes |
   | P5 repository with symlinks | a repository with links, to name |
   | P6 repository with a deep Git history | the Linux kernel |
   | P7 Windows-heavy repository | a project run on Windows, to name |

4. **The machine of each profile:** system and version, architecture. The Windows-heavy profile runs on Windows; the soak as a whole uses Windows, Linux and macOS at least once each.

## Duration

At least **seven calendar days** from the effective start, after G6, and not before every cell of the [coverage matrix](#coverage-matrix) has been exercised at least once. G7 needs every blocking incident closed. How one is closed, a fix in a later release candidate or a written acceptance, and whether such a candidate is soaked again, is the CTO's decision.

## Profiles

The thresholds below make each profile checkable; the CTO validated them on 2026-11-28.

| Profile | Definition, checked and recorded at the start |
| --- | --- |
| P1 small Go CLI | a Go module with at most 1,000 observed nodes |
| P2 TypeScript monorepo | a `package.json` workspace with at least 5 packages and a `node_modules` directory present on disk |
| P3 Flutter project | a `pubspec.yaml` with the Flutter SDK, and generated platform directories (`android/`, `ios/` or others) |
| P4 large repository | at least 100,000 observed nodes (`nodeCount` of `fingerprint --format json`) |
| P5 repository with symlinks | at least one symbolic link in the observed tree; on Windows, a junction counts |
| P6 repository with a deep Git history | at least 5,000 commits on the first-parent chain of its default branch (`git rev-list --first-parent --count HEAD`) |
| P7 Windows-heavy repository | used on Windows, with CRLF checkouts (`core.autocrlf=true`) and at least one name outside ASCII or a path longer than 200 characters |

## Binaries

Only the official `v0.4.0-rc1` archives, verified as the [acceptance packs](v0.4.0-rc1-acceptance.md#1-download-and-verify-the-draft) describe: the SHA-256 against `checksums.txt` and the attestation. Record the archive and its SHA-256 for every machine. `go install` and local builds are not soak binaries.

For a performance comparison, the same machine also keeps `v0.4.0-a8`, and `v0.3.3` for the tree outputs, from their official archives.

## Coverage matrix

Every profile exercises scenarios S1 to S7 at least once; S8 runs at least once in the whole soak. Each cell of the report records the date and the result.

| Scenario | Commands |
| --- | --- |
| S1 tree outputs | `dirloom .`, `--format json`, `--format markdown`, one graph export |
| S2 fingerprint | `dirloom fingerprint . --format json`, twice on the unchanged tree, then on another machine or system when the profile has one |
| S3 snapshot and verify | `snapshot --output`, `verify` on the unchanged tree (exit 0), after a real change (exit 1) |
| S4 diff | `diff snapshot: live:` after real work; `diff git:<a> git:<b>` across a real refactoring or merge, with move detection, and with `--no-moves` |
| S5 Git and working tree | on a clean checkout (`git status --porcelain` prints nothing): `diff snapshot:<snapshot of the checkout> git:HEAD`. Expected: no difference, exit 0, except for the documented exceptions below |
| S6 history | `history --limit 50`, and `--structural-only` |
| S7 watch (experimental) | one session of at least 30 minutes during real work, stopped with Ctrl+C |
| S8 CI use | the [CI integration](../ci-integration.md) workflow, or the same commands in the profile's own CI, for at least one profile |

**The exceptions of S5.** [Git Tree Source v1](../contracts/git-tree-source-v1.md#equivalence-with-a-checkout) does not promise equivalence with a checkout for: links checked out as files (`core.symlinks=false`, the Windows default), a junction created in the checkout, an absolute link target pointing inside the checkout, an initialized submodule, names the platform cannot materialize, the Windows hidden attribute, and files present in the checkout but not committed, such as a directory that holds only ignored files. A difference that one of them explains is recorded, not an incident; on Windows, P5 and P7 will usually show the first.

## What to record

For every run worth keeping, and for every anomaly:

- profile, machine, system and version;
- the archive and its SHA-256, and `dirloom --version`;
- the exact command, its exit code and the exit code its contract documents;
- wall time; peak memory where the system gives it: `/usr/bin/time -v` on Linux (maximum resident set size), `/usr/bin/time -l` on macOS, and on Windows the peak working set read during the run, for example with Process Explorer; the `nodeCount`;
- for an anomaly: the output, the stderr and, when it can be shared, the input that reproduces it.

## Criteria

**Incident categories** (roadmap §12.15): contract bug, correctness bug, performance issue, UX inconsistency, future enhancement.

**Main workflows:** the tree outputs, `fingerprint`, `snapshot`, `verify`, `diff` (with `git:` sources and moves) and `history`. `watch` is experimental and outside the freeze: its incidents are recorded and classified, and the CTO decides whether one blocks.

**Blocking for `v0.4.0`:** a contract bug, a correctness bug or a performance issue on a main workflow (roadmap §12.15). The table makes each one measurable; the CTO validated its thresholds, the 20% investigation threshold and the medians of five runs on 2026-11-28:

| Category | Blocking when |
| --- | --- |
| contract bug | an output breaks its written contract: a field, a value or an order the contract does not allow; an exit code or a machine code that [Exit codes and machine codes](../reference/exit-codes.md) does not document for the situation; a frozen golden that no longer matches |
| correctness bug | a wrong result: `verify` or `diff` reports a difference on an unchanged tree, or misses a real one; a move reported where there was none, or missed; the same tree gives two fingerprints on one machine; S5 reports a difference on a clean checkout; `history` reports a structural change that `diff git:<commit>^ git:<commit>` does not, or the reverse; an internal error (exit 6, or exit 1 with `internal error`), a panic, or a hang: no new output and no exit after ten times the median wall time of the same command on the same repository, or after 30 minutes without such a median |
| performance issue | a deviation of **20% or more** is the D8 investigation threshold, not a verdict: time and peaks vary by about 20% between runs of the same code. A main workflow whose median of **five runs** is at least 20% slower, or uses at least 20% more peak memory, than the median of five runs of `v0.4.0-a8` (or `v0.3.3` for the tree outputs) on the same repository and machine is investigated; it blocks when the investigation attributes it to the release candidate's code, not to the machine or the toolchain. `fatal error: out of memory` within the [documented memory](../reference/memory.md) of the workflow blocks |

**Deferrable, with a written justification in the report:** a UX inconsistency, a future enhancement, and any incident outside the main workflows that the CTO does not make blocking.

**Exit of the soak (G7):**

- at least seven days since the start date;
- every cell of the coverage matrix exercised;
- no open blocking incident;
- every deferred incident justified in writing;
- the report delivered to the CTO.
