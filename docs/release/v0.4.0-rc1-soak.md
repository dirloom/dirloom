# v0.4.0-rc1 soak protocol (D14)

> **Status:** prepared by LOT 9; the soak has not started. It starts after the publication of `v0.4.0-rc1` (G6), and its report closes gate G7 with the CTO's `v0.4.0` decision. It formalizes §5.1 of the [plan](../../.plans/v0.4.0-rc1-implementation-plan.md) and roadmap §12.15, and resolves reservation R5 once the CTO has provided the [inputs below](#inputs-from-the-cto).

The soak is real use of the published release candidate on real repositories, before `v0.4.0`. It looks for what the tests, the benchmarks and the acceptance packs cannot find.

## Inputs from the CTO

Only the CTO can provide these; the protocol does not choose them:

1. **The soak owner:** who runs it, keeps the report, and opens the incidents.
2. **One named repository for each of the seven profiles** below, with the commit or branch to start from. A repository may serve two profiles only if it meets both definitions.
3. **The machine of each profile:** system and version, architecture. The Windows-heavy profile runs on Windows; the soak as a whole uses Windows, Linux and macOS at least once each.
4. **The start date,** on or after the publication (G6).

## Duration

At least **seven calendar days** after G6, and not before every cell of the [coverage matrix](#coverage-matrix) has been exercised at least once. A blocking incident does not stop the clock, but G7 needs it closed (fixed in a later release candidate, or accepted in writing by the CTO).

## Profiles

The thresholds below make each profile checkable. LOT 9 proposes them; the CTO confirms or changes them with the inputs above.

| Profile | Definition, checked and recorded at the start |
| --- | --- |
| P1 small Go CLI | a Go module with at most 1,000 observed nodes |
| P2 TypeScript monorepo | a `package.json` workspace with at least 5 packages and a `node_modules` directory present on disk |
| P3 Flutter project | a `pubspec.yaml` with the Flutter SDK, and generated platform directories (`android/`, `ios/` or others) |
| P4 large repository | at least 100,000 observed nodes (`nodeCount` of `fingerprint --format json`) |
| P5 repository with symlinks | at least one symbolic link in the observed tree; on Windows, a junction counts |
| P6 repository with a deep Git history | at least 5,000 commits on the first-parent chain of its default branch (`git rev-list --first-parent --count HEAD`) |
| P7 Windows-heavy repository | used on Windows, with CRLF checkouts (`core.autocrlf=true`) and at least one name outside ASCII or a path longer than 200 characters |

## Binaries

Only the official `v0.4.0-rc1` archives, verified as the [acceptance packs](v0.4.0-rc1-acceptance.md#1-download-and-verify-the-draft) describe: the SHA-256 against `checksums.txt` and the attestation. Record the archive and its SHA-256 for every machine. `go install` and local builds are not soak binaries.

For a performance comparison, the same machine also keeps `v0.4.0-a8`, and `v0.3.3` for the tree outputs, from their official archives.

## Coverage matrix

Every profile exercises every scenario at least once. Each cell of the report records the date and the result.

| Scenario | Commands |
| --- | --- |
| S1 tree outputs | `dirloom .`, `--format json`, `--format markdown`, one graph export |
| S2 fingerprint | `dirloom fingerprint . --format json`, twice on the unchanged tree, then on another machine or system when the profile has one |
| S3 snapshot and verify | `snapshot --output`, `verify` on the unchanged tree (exit 0), after a real change (exit 1) |
| S4 diff | `diff snapshot: live:` after real work; `diff git:<a> git:<b>` across a real refactoring or merge, with move detection, and with `--no-moves` |
| S5 Git and working tree | on a clean checkout (`git status --porcelain` prints nothing): `diff snapshot:<snapshot of the checkout> git:HEAD` (expected: no difference, exit 0) |
| S6 history | `history --limit 50`, and `--structural-only` |
| S7 watch (experimental) | one session of at least 30 minutes during real work, stopped with Ctrl+C |
| S8 CI use | the [CI integration](../ci-integration.md) workflow, or the same commands in the profile's own CI, for at least one profile |

## What to record

For every run worth keeping, and for every anomaly:

- profile, machine, system and version;
- the archive and its SHA-256, and `dirloom --version`;
- the exact command, its exit code and the exit code its contract documents;
- wall time; peak memory where the system gives it: `/usr/bin/time -v` on Linux (maximum resident set size), `/usr/bin/time -l` on macOS, and on Windows the peak working set read during the run, for example with Process Explorer; the `nodeCount`;
- for an anomaly: the output, the stderr and, when it can be shared, the input that reproduces it.

## Criteria

**Incident categories** (roadmap §12.15): contract bug, correctness bug, performance issue, UX inconsistency, future enhancement.

**Main workflows:** the tree outputs, `fingerprint`, `snapshot`, `verify`, `diff` (with `git:` sources and moves) and `history`. `watch` is experimental and outside the freeze: its incidents are recorded and classified, and the CTO decides whether one blocks.

**Blocking for `v0.4.0`:** a contract bug, a correctness bug or a performance issue on a main workflow. Each is measurable:

| Category | Blocking when |
| --- | --- |
| contract bug | an output breaks its written contract: a field, a value or an order the contract does not allow; an exit code or a machine code that [Exit codes and machine codes](../reference/exit-codes.md) does not document for the situation; a frozen golden that no longer matches |
| correctness bug | a wrong result: `verify` or `diff` reports a difference on an unchanged tree, or misses a real one; a move reported where there was none, or missed; the same tree gives two fingerprints on one machine; S5 reports a difference on a clean checkout; `history` reports a structural change that `diff git:<commit>^ git:<commit>` does not, or the reverse; an internal error (exit 6, or exit 1 with `internal error`), a panic, or a hang |
| performance issue | a main workflow at least **20% slower**, or using at least **20% more peak memory**, than `v0.4.0-a8` (or `v0.3.3` for the tree outputs) on the same repository and machine, confirmed by a second run of both; or `fatal error: out of memory` within the [documented memory](../reference/memory.md) of the workflow |

**Deferrable, with a written justification in the report:** a UX inconsistency, a future enhancement, and any incident outside the main workflows that the CTO does not make blocking.

**Exit of the soak (G7):**

- at least seven days since G6;
- every cell of the coverage matrix exercised;
- no open blocking incident;
- every deferred incident justified in writing;
- the report delivered to the CTO.
