# v0.4.0-rc1 fuzz campaign (D9)

> **Status:** record of the bounded fuzz campaign required by decision D9 of the `v0.4.0-rc1` plan (LOT 5c). It is a record, not a contract.

## Result

All 27 fuzz targets ran for two minutes each, about 2.36 billion executions in all. **No target found a failure.** No input had to be minimized, kept as a regression case, or fixed.

## Method

Each target ran alone, one after the other, with every core:

```sh
GOTOOLCHAIN=go1.26.10 go test <package> -run '^$' -fuzz '^<Target>$' -fuzztime 2m
```

Seeds:

- the seed corpus of each target is its `f.Add` calls, in the repository;
- Go's fuzzer has no random seed to set, so a rerun explores differently;
- the generated corpus stays in Go's cache (`go env GOCACHE`, under `fuzz/`) and is not committed.

A failure would have been written to `testdata/fuzz/<Target>/` in its package, then committed as a regression case with its fix.

## The new targets

- **`FuzzResolveRevision`** runs every revision the CLI lets through (`ValidateRevision`) against the real `git`, on a repository holding:
  - a branch with two commits;
  - an annotated tag, a lightweight tag, and a tag of a tree;
  - a directory and a file.

  It requires that resolution neither panics nor hangs, and that it gives full object ids or fails with `git_revision_not_found` or `git_object_unavailable`, never an internal error. Each input starts up to four `git` processes, hence its few executions.
- **`FuzzConfigDocument`** and **`FuzzThemeDocument`** parse any document within the 1 MiB limit twice. They require the same result both times, and a refusal that is an invalid-document error. An accepted theme is also compiled, and its rules resolve a few paths.

## Limits of this campaign

- **Two minutes per target is short.**
  - `FuzzConfigDocument` and `FuzzThemeDocument` were still finding new coverage at the end (885 and 810 new corpus entries), so their exploration is not saturated.
  - `FuzzResolveRevision` ran 2,434 inputs.

  A longer run of these three before the stable release would add evidence. It is a recommendation, not a gate of D9.
- **Fuzzing finds what its properties state.** The crash sources of the D7 audit needed inputs far larger than a fuzzer produces: millions of `**`, Git bombs. Those are covered by adversarial tests (#90, #91), not by fuzzing.
- **One platform.** The record parsers are platform-free and fuzzed here. The live backends are covered by their tests on the three CI systems.
